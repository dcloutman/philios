## 1. Summary
Philios scripts can't yet store values in names other than parameters, compare values, or
express truth values. This plan adds one feature: **named values and the operators needed to
compare them**. That covers `let` variables, `const` constants (including the write-once
nullable constant), `symbol` declarations, the assignment statement, the `Boolean` and `Symbol`
types, and the `!`, `==`, and `!=` operators. The plan also adds static type checking before
execution for these constructs (D4) and structures the expression parser so that the long-term
operator precedence table (§4.12) can be added later without restructuring it (D6).

## 2. Scope and Non-goals

### 2.1 Scope
1. A stricter identifier rule for all identifiers (§4.2.1).
2. New reserved words: `let`, `const`, `true`, `false`, `symbol`, `Boolean`, and `Symbol`. `class`
   stays reserved (§4.2.2).
3. New tokens: `!`, `=`, `==`, and `!=`. Negative integer literals are also allowed at the new
   expression starts (§4.2.3, §4.2.4).
4. The `Boolean`, `?Boolean`, `Symbol`, and `?Symbol` types (§4.3).
5. `let`, `const`, and `symbol` declarations, module-level declaration semantics, scope rules,
   the one-namespace-per-scope rule, and the rule that function-scope names may not reuse
   module-level names (§4.5–§4.7, §4.9).
6. The assignment statement, including assignment to parameters (§4.8).
7. Static type checking before execution of declarations, assignments, `!` operands, and bare
   symbol names, with runtime checks for what can't be decided statically (§4.10).
8. The `!`, `==`, and `!=` operators, evaluation order, and equality semantics (§4.11), parsed
   with an extensible precedence structure (§4.12).
9. Documentation and `AGENTS.md` revisions (§7, §8 tasks T10–T11).

### 2.2 Non-goals
- Any operator not listed above, including arithmetic, comparison, `&&`, `||`, `isa`, `new`, and
  the conditional expression (D6).
- Assignment as an expression, chained assignment, and compound assignment (D7, developer draft).
- Bare symbol names in arguments, return values, conditionals, and other contexts (D18).
- Symbols that belong to a class, and classes (developer draft, D9). `class` stays reserved
  without meaning.
- Grouping parentheses in expressions (DA7).
- Static checking of the existing call-argument, return-value, `echo`-argument, and callee
  positions. These remain runtime checks (DA7).
- Repeated prefix `!` (`!!x`) (DA5).
- Assignment statements at module level, and calls of any kind in module-level initializers
  (DA1).
- Script-visible conversion of `Boolean` or `Symbol` values to `String`.
- Any change to numeric semantics or iteration order (AGENTS.md Open Decisions).

### 4.2 Lexical Rules

#### 4.2.1 Identifiers (developer draft §1; "Identifier Rule")
This rule applies to every identifier: function names, parameter names, and `let`, `const`, and
`symbol` names. It is intentionally stricter than the current rule.
- A name contains only ASCII letters (`A-Z`, `a-z`), ASCII digits (`0-9`), and underscores (`_`).
- A name may start with zero or more underscores. The first character after any leading underscores
  must be a letter.
- After that first letter, letters, digits, and underscores may appear in any order.
- Equivalent pattern: `_*[A-Za-z][A-Za-z0-9_]*`.
- Names are case-sensitive: `foo`, `Foo`, and `FOO` are three different names.
- Reserved words can't be used as names. This is a syntax error at the word, as today.
- The lexer still reads a maximal word `[A-Za-z_][A-Za-z0-9_]*`. A word that is not a reserved
  word and does not match the pattern above is a **lexical error** at the word's first byte, with
  the message `invalid identifier`. A digit-initial word such as `1count` remains the existing
  lexical error for a literal followed by an identifier character.

| Name | Valid? | Reason |
|---|---|---|
| `count` | Yes | |
| `_count`, `__count` | Yes | Leading underscores followed by a letter |
| `count_2`, `a1b2` | Yes | Digits and underscores after the first letter |
| `_`, `__` | No | No letter |
| `1count` | No | Starts with a digit |
| `_1count` | No | A digit comes before the first letter |

#### 4.2.2 Reserved Words (D9; developer draft "New reserved words")
The 28 current reserved words stay reserved, including `class`. These 7 are added, for a total of
35: `let`, `const`, `true`, `false`, `symbol`, `Boolean`, and `Symbol`.
- `true` and `false` are **reserved literal keywords**. They are not global symbols, bindings, or
  variables. Each is a literal expression of type `Boolean`, like `null` (D20).
- `Boolean` and `Symbol` are type names (D9, D10, D14). Every current type name is a reserved
  word with its own token kind, so `Symbol` is reserved too (see OQ-15).
- The draft's list was not complete (D9). Other words may be reserved by later plans.
- Each new word gets its own token kind. The lexer never emits a reserved word as an identifier
  (plan 0001 D27).

#### 4.2.3 New Tokens
| Token | Text | Use in this plan |
|---|---|---|
| `Bang` | `!` | Prefix logical NOT |
| `Assign` | `=` | Declaration initializer and assignment statement only |
| `EqualEqual` | `==` | Equality |
| `BangEqual` | `!=` | Inequality |

- Tokens use maximal munch: `==` and `!=` are single tokens when their characters are adjacent.
  Thus `===` lexes as `==` followed by `=`, `!==` as `!=` followed by `=`, `= =` as two `=`,
  and `! =` as `!` followed by `=`. The grammar rejects these sequences (§5).
- `?` keeps its plan 0002 rule. It is valid only as the adjacent prefix of a nullable type name,
  which now includes `?Boolean` and `?Symbol`.
- `;` line continuation works between any two tokens, as today. For example, a line may end with
  `==` followed by `;`.

#### 4.2.4 Negative Integer Literals
The rule "a negative integer literal is allowed only where an expression starts" now includes the
new expression starts. A negative literal may directly follow `return`, `(`, `,`, `=`, `==`,
`!=`, or `!`. All other plan 0002 rules for negative literals are unchanged (`-0`, range limits,
a following identifier character). Every other `-` is still a syntax error.

### 4.3 Types (D9, D10, D14)

| Declared type | Accepts runtime values of class |
|---|---|
| `Integer` | `Integer` |
| `String` | `String` |
| `Function` | `Function` |
| `Boolean` | `Boolean` |
| `Symbol` | `Symbol` |
| `Object` | `Integer`, `String`, `Function`, `Boolean`, `Symbol` (every non-`null` value) |
| `null` | `null` only |
| `?T` for each `T` except `null` | the values `T` accepts, plus `null` |

- `Boolean` extends `Object`. Its only values are `true` and `false`. It is immutable and compares
  by value (D9, D11). Only `?Boolean` accepts `null` (D10).
- `Symbol` extends `Object`. Its values are symbols created by `symbol` declarations (§4.9). A
  `Symbol` variable may hold a symbol (D9, D14).
- All the types above may be used for parameters, return types, `let`, and `const` (D10).
  `?null` and the non-declarable reserved type words remain syntax errors.
- `typeof` returns `"Boolean"` for a `Boolean` value and `"Symbol"` for a `Symbol` value. Its other
  results are unchanged.
- Runtime representation (architecture, not script-visible): `Boolean` and `Symbol` are new
  object-model classes with new `ObjectType` tags. No `Boolean` instance may be process-global or
  `static` (AGENTS.md Core Architectural Constraint 1). Canonical `true` and `false` instances,
  if any, are owned by the `ExecutionContext`, like the `null` instance. Otherwise each literal
  evaluation creates a new object, like `Integer` literals do.

### 4.4 Grammar
This extends the grammar in `src/frontend/parser/parser.cpp`. `typeName` gains `Boolean` and
`Symbol` as base words and as nullable bases.

```
program      := { moduleItem } EOF
moduleItem   := functionDecl | constDecl | symbolDecl            // D13; `let` here is an error
statement    := returnStmt | passStmt | letDecl | constDecl | symbolDecl
              | assignStmt | exprStmt
letDecl      := 'let'    IDENT ':' typeName [ '=' expression ] NEWLINE
constDecl    := 'const'  IDENT ':' typeName [ '=' expression ] NEWLINE
symbolDecl   := 'symbol' IDENT NEWLINE
assignStmt   := IDENT '=' expression NEWLINE                     // D7: statement only
exprStmt     := ( callExpr | pseudoCall ) NEWLINE                // unchanged
expression   := equality                                         // entry point for §4.12
equality     := unary { ( '==' | '!=' ) unary }                  // left-associative (D16)
unary        := '!' primary | primary                            // DA5: no `!!x`
primary      := INTEGER | STRING | 'null' | 'true' | 'false'
              | IDENT | callExpr | pseudoCall
```

- An `expression` appears in the same places as today (return value, call and pseudo-call
  arguments), and also as a declaration initializer and as an assignment's right-hand side.
- The operand of `!` is a `primary`, so it can't start with `!` (DA5, consistent with level 5 of
  the long-term table being non-associative). `!!x` and `! !x` are syntax errors at the second
  `!`, with the message `repeated ! is not allowed` (§5.2). A `!` inside a call argument starts a
  new expression, so `!f(!x)` is valid.
- `=` never appears inside an `expression`. `echo(a = 1)`, `f(a = 1)`, `return a = 1`,
  `a = b = 1`, and `let x: Integer = y = 1` are syntax errors at the offending `=` (D7).
- An expression statement is still only a call or a pseudo-call. `a == b`, `!a`, `a`, and `true`
  alone on a line are syntax errors (§5). A statement that starts with an identifier is a call if
  the next token is `(` and an assignment if it is `=`. Any other next token is a syntax error at
  that token.
- `a == b == c` parses as `((a == b) == c)`. `!a == b` parses as `((!a) == b)` because `!` binds
  tighter than `==` (§4.12). `a == !b` is valid.

### 4.5 Scopes, the Namespace Rule, and No Shadowing (D13, D19, DA1, DA3)
- **Scopes in this plan:** the module scope, and one function scope per function body. The function
  scope holds the parameters and every declaration in the body. No other blocks exist yet. A future
  nested block gets its own scope (D13).
- **Module scope** may contain function, `const`, and `symbol` declarations. Classes come later.
  `let` at module scope is a syntax error at `let` (D13).
- **Function scope** may contain `let`, `const`, and `symbol` declarations. Nested function
  declarations remain a syntax error.
- Variable declarations always begin with `let` and constants always begin with `const`, wherever
  they are declared (D13).
- **One namespace per scope (D19):** function names, parameters, and `let`, `const`, and `symbol`
  names share one namespace in each scope. A second declaration of a name in the same scope is a
  declaration error at the second name, whatever kinds the two declarations are.
- **No shadowing of module-level names (DA3, corrected 2026-11-21):** a function's parameters
  and its `let`, `const`, and `symbol` declarations may **not** reuse a name declared at module
  level. The module-level names are every module function name (including the function's own
  name and `main`), every module-level constant, and every module-level symbol; module-level
  classes will join this set when a later plan adds them. A violation is a declaration error at
  the function-scope name, with the message `name must not match a module-level declaration`.
  - This keeps and generalizes the plan 0001 D15 rule that a parameter must not match a module
    function name. The validator check stays (task T6), now covers all module-level names and
    all function-scope declarations, and uses the new message. The existing CLI case
    `t_decl_2_parameter_named_like_function` (declaration error at line 3, column 12) keeps its
    expectation unchanged (task T10).
  - **Order-independent:** the rule applies whether the module-level declaration comes before or
    after the function in the file. This follows the correction's wording, which has no order
    qualification, and matches DA1 c, under which every module-level name is visible in every
    function body. The validator therefore collects all module-level names before it checks any
    function.
  - The rule applies in every function, including functions that are never called.
  - **Check order at each function-scope name:** first the `main` rule below (existing message),
    then the same-scope duplicate rule (D19, `duplicate declaration`), then this rule. So a
    parameter named `main` keeps its existing error and location, and a name that is both a
    same-scope duplicate and a module-level name reports the error at whichever occurrence comes
    first in source order (the first occurrence fails this rule).
  - **When it is reported:** for each function, the validator checks every function-scope name
    (the parameters in order, then the body's `let`, `const`, and `symbol` names in source
    order) against these rules **before** it checks any statement or expression in that body.
    A name error in a function is therefore reported before any use or type error in the same
    function. Functions and module-level initializers are still checked in source order.
- **Duplicates within one scope (D19)** remain errors, as stated above.
- **Name resolution:** because function-scope names and module-level names never coincide, every
  name inside a function body has exactly one candidate binding. A use resolves to the
  function-scope binding if the function scope declares the name, and otherwise to the
  module-level binding. The validator and the runtime (`Environment::lookup`, which searches the
  call environment before the module environment) agree trivially.
- **Visibility within a function scope:** a parameter is visible in the whole body. A `let`,
  `const`, or `symbol` name becomes visible in the statement after its declaration. A use or
  assignment of the name before then, including in its own initializer (`let x: Integer = x`), is a
  declaration error at that use, with the message `used before declaration` (developer draft §2).
  Because a function-scope name can't match a module-level name, such an earlier use can never
  fall back to a module-level binding.
- **Module-level names in function bodies (DA1 c):** every module-level function, constant, and
  symbol is visible in every function body, including bodies that appear before its declaration,
  because all module-level initializers run before `main` is called (§4.5.1).
- `main` may still be used only as its function declaration name. A parameter, `let`, `const`, or
  `symbol` named `main` is a declaration error at the name, with the existing `main` message
  (`main may be used only as its declaration name`).

#### 4.5.1 Module-Level Declarations (DA1)
- **When they run (DA1 a):** after the whole program passes lexing, parsing, and validation, the
  module-level `const` and `symbol` declarations execute **once, in source order**, in the module
  environment. Then `main` is called. Each `symbol` declaration creates its symbol at this point.
- **What an initializer may contain (DA1 b):** a module-level initializer may contain only
  integer, string, `null`, `true`, and `false` literals; `!`, `==`, and `!=`; and the names of
  module-level constants and symbols declared **earlier** in the file. Anything else is a
  declaration error at the first byte of the offending construct, with the message
  `not allowed in a module-level initializer`: a call, an `echo` or `typeof` pseudo-call, or a
  function name used as a value. A name of a module-level constant or symbol declared later, or
  the declaration's own name, is a declaration error at the use, with `used before declaration`.
  Because no calls are allowed, no script code and no output happen before `main`.
- The usual checks apply to module-level initializers: §4.10 static checks, bare-symbol placement
  (§4.9), and the nesting limit (§6.1).
- **Runtime failures:** a runtime-checked initializer (for example `const b: Boolean = !o` where
  `o` is a module-level `Object` constant holding `1`) raises its runtime error (§5.4, exit 70)
  during module initialization. `main` is not called, and stdout is empty.
- **No writes from functions (DA1 d):** a function may not assign to any module-level constant,
  including a nullable one that is still unassigned. Such an assignment is a declaration error at
  the target (`cannot assign to constant`). Module scope has no assignment statement, so a
  module-level nullable constant without a non-null initializer stays `null` permanently (a
  consequence of DA1 d; D12 already calls null constants bad practice).
- A function can't declare a local with a module-level constant's name (DA3, §4.5), so an
  assignment in a function to a module-level constant's name always targets the module-level
  constant and is always the `cannot assign to constant` error.

### 4.6 `let` Declarations (developer draft §2; D13)
- Syntax: `let <name>: <Type>` or `let <name>: <Type> = <expression>`. The type annotation is
  required.
- `?` before the type makes it nullable: `let name: ?String` accepts a `String` or `null`.
- A variable with a non-nullable type, including `null`, must be initialized in its declaration.
  `let name: String` is a declaration error at `let`.
- A variable with a nullable type may omit the initializer. It then starts as `null` (developer
  draft, "Uninitialized nullable variables").
- The initializer is checked against the declared type as in §4.10.
- Execution: evaluate the initializer if there is one, check its value (§4.10), then bind the name
  in the current scope. Without an initializer, bind `null`.
- `let` variables are mutable and may be reassigned any number of times (§4.8).

```
let count: Integer = 0      // valid
let name: ?String           // valid: nullable, no initializer; starts as null
let title: ?String = null   // valid
let label: String           // declaration error: non-nullable type without an initializer
```

### 4.7 Constants (developer draft §4; D3, D8, D12, D13, D15)
- Syntax: `const <name>: <Type> = <expression>`, or `const <name>: ?<Type>` for a nullable type.
  Naming, type annotation, and scope rules are the same as for `let`. A constant may also be
  declared at module scope (D13), with the rules in §4.5.1 (DA1).
- **Non-nullable constants**, including the type `null`: the initializer is required. Omitting it
  is a declaration error at `const`. Any assignment after the declaration is a declaration error at
  the assignment target.
- **Nullable constants (`?T`): one write-once rule.**
  1. `null` means the constant is **unassigned** (D8).
  2. The initializer may be omitted. An initializer that is the literal `null` does nothing and
     equals omitting it. The constant starts unassigned (D12).
  3. Once the constant holds a non-null value, the value is permanent. Any later assignment is an
     error (D12). So, in practice, a non-null value can be written only once: by a non-null
     initializer or by one later assignment.
  4. Assigning `null` after the declaration is always an error, even while the constant is still
     unassigned (D8).
  5. The value written, by a later assignment or by an initializer other than the literal `null`,
     must have a static type that is non-null: `T`, a subtype of `T`, or a non-null supertype of
     `T` that is checked at runtime (§4.10). A right-hand side whose static type is nullable (`?U`
     or `null`) is a declaration error, even if its value might be non-null at runtime (D15).
- **Detection.** No conditionals or loops exist yet, so each statement in a function body runs
  once, in order. The validator therefore tracks each function-scope nullable constant as
  *unassigned* or *assigned* through the body. A write to an *assigned* constant is a declaration
  error at the target. Module-level constants can't be written at all after their declaration
  (§4.5.1, DA1 d). The runtime also enforces rules 3 and 4 as a defense-in-depth backstop (§4.8,
  §5.4). With the rules in this plan, a validated program can't reach that backstop; it guards
  against validator defects and against later plans that add control flow.
- Each call creates a fresh function scope, so a function-scope constant starts unassigned on each
  call.
- Practice note from the developer (D12): null constants are usually a bad idea, and symbols are
  usually the better tool.

```
const limit: Integer = 10       // valid
const tag: ?String              // valid: unassigned (null)
tag = "a"                       // valid: the one non-null write
tag = "b"                       // declaration error: tag already holds a non-null value
const other: ?String = null     // valid: same as no initializer
other = null                    // declaration error: null cannot be assigned to a constant
const count: Integer            // declaration error: non-nullable constant without initializer
```

### 4.8 Assignment (developer draft §3; D5, D7)
- Syntax: `<name> = <expression>`. Assignment is a **statement only**. It produces no value,
  can't be chained, and can't appear inside an expression (D7).
- The target must be a visible `let` variable, a parameter (DA2), or a function-scope constant
  that may still be written (§4.7). The target name is resolved as in §4.5. Otherwise the
  statement is a declaration error at the target:
  - an undefined name, or a name used before its declaration (§4.5);
  - a function name, or `main`;
  - a symbol name (D14);
  - a non-nullable constant, a nullable constant that is already *assigned* (§4.7), or any
    module-level constant (DA1 d).
- **Parameters (DA2):** a parameter behaves like a `let` variable of its declared type. It may be
  reassigned any number of times, and each assignment is checked against its declared type like a
  `let` assignment. Assigning a parameter changes only the callee's binding; the caller's
  argument expression and bindings are unaffected.
- The value must be accepted by the target's declared type. A nullable target also accepts `null`
  (except nullable constants, §4.7). A static mismatch, or a statically nullable value for a
  non-nullable target (DA6), is a declaration error. A value that can only be checked at runtime
  raises a runtime error if it doesn't match (§4.10).
- **Execution order (D5):**
  1. Check that the target is assignable. For a nullable constant, the runtime checks that its
     current value is `null`. If it isn't, a runtime error is raised **before** the right-hand side
     is evaluated.
  2. Evaluate the right-hand side completely.
  3. Check the value: for a nullable constant, a `null` value is a runtime error. Then check that
     the declared type accepts the value.
  4. Store the value. For a constant, the store re-checks that the current value is still `null`.
     If it isn't, the store raises the same runtime error as step 1, and nothing is stored (§6).
     Under this plan no script code run by the right-hand side can write the target (function
     scopes are private to their call, there are no closures, and functions can't write
     module-level constants), so this re-check is defense in depth.
- If any step fails, the target keeps its previous value.

### 4.9 Symbols (developer draft §5; D9, D14, D17, D18, D19)
- Syntax: `symbol <name>`. There is no type annotation and no initializer. `symbol x = 1` and
  `symbol x: Symbol` are syntax errors at the token after the name.
- `symbol name` declares a unique, immutable symbol value bound to `name` (D14). Naming rules,
  scope, the namespace rule, and the no-shadowing rule (§4.5) are the same as for variables and
  constants. A symbol
  may be declared at module scope (D13, §4.5.1) or in a function scope.
- **Creation (DA1 a, DA4):** a module-level `symbol` declaration creates its symbol once, during
  module initialization. A function-scope `symbol` declaration creates a **new** symbol every time
  it executes, that is, once per call. Symbols from two calls are never equal.
- Assigning a value to a symbol name is a declaration error at the name (D14).
- Symbols compare by identity: a symbol is equal only to itself (D11, D14).
- **Where a bare symbol name is legal (D17, D18).** In this plan, a bare symbol name, meaning an
  identifier that resolves to a `symbol` declaration, may appear only:
  1. as the whole right-hand side of a `let` or `const` initializer, or of an assignment, whose
     target type is `Symbol` or `?Symbol` (DA7); and
  2. as an operand of `==` or `!=`.

  Any other use is a declaration error at the name before execution. That includes an `Object` or
  `?Object` target (D17), function arguments, `echo` or `typeof` arguments, `return`, the operand
  of `!`, and a callee (D18).
- A `Symbol`-typed variable that holds a symbol is an ordinary value. It may be passed, returned,
  compared, given to `typeof` (which returns `"Symbol"`), or assigned to `Object` (D17).

```
symbol philiosIsRad
let foo: Symbol = philiosIsRad      // valid (D14)
let bar: Object = foo               // valid: a Symbol variable widens to Object (D17)
let baz: Object = philiosIsRad      // declaration error: bare symbol to Object (D17)
let same: Boolean = foo == philiosIsRad   // valid: true
echo(philiosIsRad)                  // declaration error: bare symbol as an argument (D18)
philiosIsRad = foo                  // declaration error: assignment to a symbol (D14)
```

### 4.10 Static Types and Type Checking (D4, D15, D17, D18, DA6, DA7)
Typing is mandatory. The interpreter detects as much as it can before execution, from declared
types, including the declared return types of functions. It checks at runtime what it can't decide
before execution (D4). Static checks run in the validation phase, cover every function including
uncalled ones and every module-level initializer, and report the first error in source order as a
`declaration` error (exit 65; DA7).

**Static type of an expression.** Names are resolved as in §4.5.

| Expression | Static type |
|---|---|
| integer literal / string literal / `null` / `true` or `false` | `Integer` / `String` / `null` / `Boolean` |
| a name resolving to a parameter, `let` variable, or constant (function- or module-level) | its declared type |
| a name resolving to a module function, used as a value | `Function` |
| a name resolving to a `symbol` declaration | *symbol name* (special; only §4.9 contexts) |
| a call whose callee resolves to a module function | that function's declared return type |
| any other call (callee resolves to a parameter, variable, or constant) | *dynamic* (unknown) |
| `echo(...)` / `typeof(...)` | `null` / `String` |
| `!e`, `a == b`, `a != b` | `Boolean` |

**Checking an expression of static type `S` against an expected declared type `E`.** Let `V(T)` be
the set of runtime classes that a declared type `T` accepts (§4.3).
1. If `S` is a *symbol name*, the expression is valid only in the §4.9 contexts. Otherwise it is a
   declaration error at the name.
2. If `S` is *dynamic*, the check happens at runtime.
3. If `V(S) ⊆ V(E)`, the expression is valid, and no runtime failure is possible.
4. If `V(S) ∩ V(E)` is empty, so that no value can satisfy both types, the expression is a
   declaration error at its first byte. Examples: `String` against `Integer`, and `null` against
   `Integer`.
5. Otherwise, `S` overlaps `E` but is wider, as `Object` against `Integer` or `?Integer` against
   `Integer` are. The check happens at runtime (D4), except in these places, where a **nullable**
   `S` (`?U` for any `U`) is a declaration error at the expression's first byte:
   - **`!` operand** (D4): message `operand of ! must be Boolean`.
   - **Nullable-constant write** (D15, §4.7 rule 5): message `constant value must not be null`.
   - **Non-nullable target (DA6):** the initializer of a `let` or `const` whose declared type is
     not nullable, or the right-hand side of an assignment whose target (a `let` variable or a
     parameter) has a non-nullable declared type. Message: `nullable value for non-nullable
     target`. Examples: `let i: Integer = q()` with `q(): ?Integer`, and `let o: Object = n` with
     `n: ?String`. The developer stated DA6 for `let` and assignment targets "to match D15"; this
     plan applies it to non-nullable `const` initializers and to parameter targets too, for
     consistency (OQ-19).

   A non-nullable but wider `S` (for example `Object` against `Integer`) stays a runtime check.
   A *dynamic* `S` stays a runtime check (rule 2), even if the value turns out to be `null`.
- A runtime check uses the existing single acceptance function, `matchesDeclaredType`, extended for
  `Boolean`, `Symbol`, and `Object` (§4.3). A failure is a runtime error at the expression's first
  byte (§5).
- Contexts that use these checks in this plan: `let` and `const` initializers (function- and
  module-level), assignment right-hand sides, `!` operands (with `E` = `Boolean`), and
  bare-symbol placement. Call arguments, return values, `echo` arguments, and callees keep their
  current runtime checks (DA7).
- `==` and `!=` place no type restriction on their operands. Comparing operands whose static types
  are disjoint is valid and yields `false` for `==` (developer draft §7).

### 4.11 Operators

#### 4.11.1 Logical NOT `!` (developer draft §6; D4, D5)
- `!` is a prefix operator. `!true` is `false`, and `!false` is `true`.
- The operand must be a `Boolean`. Static checking follows §4.10 with `E = Boolean`. For example,
  `!1`, `!"a"`, `!null`, `!` applied to `?Boolean`, and `!` applied to a bare symbol are
  declaration errors at the operand's first byte. An operand of static type `Object`, or a dynamic
  call, is checked at runtime. A value that is not a `Boolean` raises a runtime operand-type error
  at the operand's first byte.
- Evaluation: evaluate the operand completely, check it, then produce the negation.
- The operand can't itself be a `!` expression: `!!x` is a syntax error at the second `!` (DA5,
  §4.4, §5.2).

#### 4.11.2 Equality `==` (developer draft §7; D11, D16)
- `a == b` is `true` only if both operands have the same **runtime** class and are equal under D11.
- If the runtime classes differ, the result is `false`. This is not an error. Example: `1 == "1"`
  is `false`.
- **D11 equality:**
  - `Integer`: equal if the values are equal.
  - `String`: equal if the byte sequences are equal. The length is compared, then the bytes.
  - `Boolean`: equal if both are `true` or both are `false`.
  - `null`: `null == null` is `true`.
  - `Function`, `Symbol`, and every other reference-like value, including future class instances:
    equal only if both operands are the same instance (D11).
- **Static types don't affect equality** (D21). The draft's sentence "A subtype cannot be equal
  to a supertype" is removed. Equality depends only on the two runtime values (D11). So a value
  held in an `Object` variable equals the same value held in a variable of its exact type. For
  example, with `let o: Object = 1`, `o == 1` is `true`. Equality never recurses into a value's
  contents.
- Chains are allowed and left-associative: `a == b == c` is `((a == b) == c)` (D16). For example,
  `1 == 1 == true` is `true`, and `1 == 1 == 1` is `false` because `Boolean` is not `Integer`.

#### 4.11.3 Inequality `!=` (developer draft §8)
- `a != b` is always the opposite of `a == b`. It has the same precedence and associativity as
  `==`, and the two may be mixed in a chain: `a == b != c` is `((a == b) != c)`.

#### 4.11.4 Evaluation Order (D5)
- The left operand is evaluated completely before the right operand. If evaluating the left operand
  raises an error, the right operand is not evaluated.
- In a chain `((a == b) == c)`, the order is `a`, `b`, the comparison of `a` and `b`, `c`, and then
  the final comparison.
- The C++ evaluator must sequence these steps explicitly (style guide, CERT EXP50).
- Assignment order: see §4.8.

#### 4.11.5 Interaction with `echo` and `typeof`
- `typeof(e)` accepts any expression except a bare symbol name (D18). `typeof(1 == 1)` and
  `typeof(!true)` return `"Boolean"`.
- `echo(true)` and `echo(false)` are syntax errors at the argument, which extends the plan 0002 D16
  literal rule (DA7). Any other non-`String` argument keeps today's runtime argument-type
  error.

### 4.12 Extensible Precedence Structure (D6, D16)
The developer's long-term precedence table (grill record, "Long-Term Operator Precedence") is
**design guidance only**. This plan implements only `!` (level 5, non-associative, so `!!x` is
rejected per DA5) and `==`/`!=` (level 9). For this plan, D16 replaces level 9's "Non-associative"
with left-associative. Assignment (level 13) is a statement here (D7).
- The parser must have one parse function per precedence level, or a single table-driven
  precedence-climbing loop. In either structure, each level delegates to the next tighter level, so
  a later plan can insert levels 1–4, 6–8, and 10–12 without restructuring existing levels.
- The AST uses one unary-operator node and one binary-operator node, each carrying an operator
  enumerator. It does not use one node class per operator, so new operators add enumerators, not
  node classes.

### 4.13 Runtime Model Summary
- Module-level constants and symbols are bound in the module environment, which already holds the
  functions, during module initialization (§4.5.1).
- Function-scope declarations are bound in the call environment, which already holds the
  parameters (§4.5). Each call gets a fresh call environment, so function-scope constants start
  unassigned and function-scope symbols are new on each call (DA4).
- An environment binding records its kind (`parameter`, `let`, `const`, `symbol`, or `function`)
  and its declared type, so that assignment can be checked at runtime (§4.8). Parameters are
  assignable (DA2). Lookups still return owning copies, and still search the call environment
  before the module environment. Because the validator forbids function-scope names that match
  module-level names (DA3), the two environments never hold the same name. The exact binding
  record and `Environment` interface are in §4.14.3.
- A constant's state needs no extra flag: `null` means unassigned (D8).

### 4.14 Component Contracts (architecture decisions AD1 and AD2)
These contracts answer the two High findings of the architecture review, round 1, and (in the
"Name storage" part of §4.14.2) the High finding of the security review, round 1. They are
architecture only and change no script-visible behavior. The composer decided them from the
current code (§10.3). File paths are relative to the repository root.

#### 4.14.1 Validator-to-Evaluator Contract for Runtime Checks (AD1)
- **No validator artifact.** The validator writes nothing into the AST and returns nothing.
  `void validateProgram(const Program& program)` in
  `src/analysis/semantic_analyzer/validator.hpp` keeps its signature: it returns if the program
  is valid and throws `DeclarationError` (or `InternalError`) otherwise. The static types of
  §4.10 are computed inside `validator.cpp` and discarded when it returns. AST nodes stay
  immutable after parsing: no `mutable` fields, no annotation pass, and no side table keyed by
  node address.
- **The evaluator always performs the §4.10 runtime checks.** At every site in the table below,
  the evaluator runs the listed check unconditionally, through the single acceptance function
  `matchesDeclaredType` (or an `ObjectType` test for `!`). It never asks whether the validator
  proved the site safe. This is the model the current code already uses for argument and
  return checks (`src/runtime/evaluator/call.cpp`).
- **Why this matches "check at runtime only what can't be decided before execution" (§4.10, D4).**
  Static soundness: the runtime value of every expression is accepted by its static type
  (§4.10 table). Literals have their own class. A parameter, `let`, or constant holds only values
  its declared type accepted at binding or assignment, which the checks below and the existing
  argument check enforce. A call to a module function returns only values its declared return
  type accepts, which the existing return check enforces. `echo` returns `null`, and `typeof`
  returns a `String`. So at a site where §4.10 rule 3 applies, the runtime check always passes.
  Sites where rule 1, 4, or 5 applies are declaration errors and never run. A runtime check can
  fail only at the sites that §4.10 sends to runtime (rule 2 and the non-nullable part of rule
  5). Observable behavior is the same as checking only those sites. The extra cost is one
  `ObjectType` comparison per checked site.
- **Expected-type sources and checks, in order:**

  | Site | Expected type comes from | Runtime checks, in order | Failure |
  |---|---|---|---|
  | `LetDecl` initializer | `LetDecl::type()` (the parsed `DeclaredType`) | `matchesDeclaredType(value, type)` | `AssignmentType` at the initializer's first byte |
  | `ConstDecl` with a nullable type and no initializer, or with an initializer that is a `NullLiteral` node (§4.7 rule 2) | none | none; the initializer is not evaluated, and the constant is bound to `context.nullObject()` | none |
  | Any other `ConstDecl` initializer | `ConstDecl::type()` | 1. if the type is nullable and the value is `null`: fail with `ConstantNullWrite` (§4.7 rule 5); 2. `matchesDeclaredType(value, type)` | `ConstantNullWrite` or `AssignmentType`, at the initializer's first byte |
  | `AssignStmt` right-hand side | the target binding's declared type, from `Environment::bindingInfo` (§4.14.3) | the §4.8 steps, as specified in §4.14.3 | §4.8 and §5.4 |
  | `UnaryExpr` with `Not` | fixed: `Boolean` | `value.objectType() == ObjectType::Boolean` | `OperandType` at the operand's first byte |
  | Call arguments, return values, `echo` arguments, callees | unchanged (DA7) | unchanged | unchanged |

- **Validator guarantees the evaluator may rely on.** A violation of any of these is an
  `InternalError`, never a script error: every `Identifier` evaluated resolves through
  `Environment::lookup`; every `AssignStmt` target resolves to a `Parameter`, `Variable`, or
  `Constant` binding (a `Function` or `Symbol` binding as the target is an `InternalError`);
  `SymbolDecl`, `LetDecl`, and `ConstDecl` names are not already bound in the environment they
  are defined in. Name, visibility, bare-symbol, `main`, and module-level-initializer rules are
  checked only by the validator. The constant write-once checks (§4.8 steps 1 and 4) stay real
  runtime errors (`ConstantReassignment`) as defense in depth (§4.7), and are not
  `InternalError`s.
- **Rejected alternatives.** (a) Check-mode or expected-type fields on AST nodes: nodes are
  `const` after parsing, and each `FunctionDecl` is shared with its runtime `Function` (D3), so
  the validator would need `mutable` fields or a second, mutating parse step, and the AST would
  carry analysis state. (b) A validator-returned side table: a new artifact whose lifetime would
  have to be tied to the `Module` and its AST, a lookup on every evaluation, and a silently
  skipped check whenever an entry is missing. Both add state whose only effect is to skip a
  check that costs one tag comparison.

#### 4.14.2 Module Items and Declaration Ownership (AD2)
- **Representation** (`src/frontend/ast/ast.hpp`, replacing the current `Program` alias):

  ```cpp
  /// @brief One `moduleItem` (§4.4): a FunctionDecl, ConstDecl, or SymbolDecl.
  using ModuleItem = std::shared_ptr<const ASTNode>;

  /// @brief The parsed `program` production: every module item in source order.
  using Program = std::vector<ModuleItem>;

  /// @brief The FunctionDecl that @p item points to, sharing ownership with @p item, or null if
  ///        @p item is not a FunctionDecl. Uses `kind()` and `std::static_pointer_cast`.
  /// @throws InternalError if @p item is null.
  [[nodiscard]] std::shared_ptr<const FunctionDecl> asFunctionDecl(const ModuleItem& item);
  ```

  Invariant: every item is non-null, and its `kind()` is `NodeKind::FunctionDecl`,
  `NodeKind::ConstDecl`, or `NodeKind::SymbolDecl`. The parser guarantees it. The validator and
  `Module::load` check it and throw `InternalError` on a violation. Dispatch over items uses
  `kind()` and a `switch` that handles every `NodeKind` explicitly, as the validator does today.
- **Ownership.** The parser creates each module item with `std::make_shared<const FunctionDecl>`,
  `std::make_shared<const ConstDecl>`, or `std::make_shared<const SymbolDecl>`. The `Program`
  holds one strong reference to each item.
  - **FunctionDecl:** a runtime `Function` holds the `std::shared_ptr<const FunctionDecl>` that
    `asFunctionDecl` returns. That pointer shares the item's control block, so the `Function`
    and the `Program` share ownership of the declaration exactly as today (D3). The `Function`
    class, its constructor, `callFunction`, and `runMain` keep their current interfaces.
  - **Module-level ConstDecl and SymbolDecl:** owned only by the `Program`. No runtime object
    refers to them. A binding stores its `BindingKind` and `DeclaredType` by value (§4.14.3), and
    a `Symbol` object holds no AST pointer and no view into the source buffer; it is pure
    identity (T4).
  - **Function-scope declarations and statements** (`LetDecl`, `ConstDecl`, `SymbolDecl`,
    `AssignStmt`) are owned by their `Block` through `std::unique_ptr<ASTNode>`, like every
    current statement. The same `ConstDecl` and `SymbolDecl` classes serve both scopes.
- **Name storage: the AST owns its text (security review round 1).** Every AST node that has a
  name stores it as an owned `std::string`, never as a `std::string_view` into the source
  buffer. This covers the existing `Identifier`, `Param`, and `FunctionDecl` and the new
  `LetDecl`, `ConstDecl`, `SymbolDecl`, and `AssignStmt` (its target name). Each constructor
  keeps its `std::string_view name` parameter and copies it. Each `name()` accessor keeps its
  `[[nodiscard]] std::string_view name() const noexcept` signature but returns a view into the
  node's own member, valid while the node lives. As a result, the `Identifier` and `Param`
  constructors are no longer `noexcept`: they may throw `std::bad_alloc`, like the
  `FunctionDecl` constructor. Destructors stay `noexcept` and allocate nothing, because
  destroying a `std::string` does neither. String literal bytes are already owned
  (`StringLiteral`), and `SourceLocation` holds only line and column, so after this change **no
  AST node refers to the source buffer**. Only tokens do, and tokens live only inside
  `Module::load` (and the test pipeline).
  - *Why owned names rather than a shared source buffer.* The alternative was to make the
    buffer a `std::shared_ptr<const std::string>` and give every `FunctionDecl` (and any later
    node that can escape the `Module`) a strong reference to it. That keeps a lifetime rule
    that each future escaping node must remember. It also changes the `Parser`, `FunctionDecl`,
    test-builder, and test-pipeline interfaces to pass the buffer through. Owned names remove the
    borrowed-view hazard from the AST entirely and add no ownership edge, back-edge, or
    reference count. Interfaces stay the same apart from the constructors' exception
    specifications. The cost is parse-time copies of names and 8 to 16 extra bytes per named node
    (`std::string` is 24 bytes in libc++ and 32 in libstdc++, against 16 for a
    `std::string_view`, on 64-bit targets). Names that fit the small-string buffer (at least 15
    bytes in libstdc++) do not allocate. Evaluation and lookup
    costs do not change, because `Environment` already copies names into its own `std::string`
    keys and every lookup still takes a `std::string_view`.
  - *The hazard already exists in the current code (plans 0001 and 0002), but nothing triggers
    it yet.* `Function` already co-owns its `FunctionDecl` (D3). `Module::~Module` frees the
    buffer, and `ast.hpp` only *documents* that no node may outlive the `Module`. No script or
    CLI path keeps a `Function` past the `Module`: `runMain` returns an `int`, and the CLI
    destroys the `Module` last. But the C++ interface allows it: look up a `Function` through
    `Module::environment()`, then destroy the `Module`. Then reading `declaration()->name()` or
    calling the function reads freed memory. This plan adds no new way for a `Function` to
    escape (a module-level constant can't hold a `Function`, OQ-20). It fixes the hazard because
    this plan adds four more name-holding node classes, and the security review requires a
    retained `Function` to stay safe.
  - The ownership graph does not change. `Function` → `FunctionDecl` → owned children is the
    only edge from runtime into the AST, as before. No edge is weakened, and nothing points back
    from the AST to the `Module`. The parser still passes each token's text to the node
    constructor, which copies it, so the parser's interface does not change.
- **Destruction.** Every new node class that has children (`LetDecl`, `ConstDecl`, `AssignStmt`,
  `UnaryExpr`, and `BinaryExpr`) implements `detachChildren` and defines a `noexcept`
  destructor that moves its children onto a local worklist and runs `destroyWorklist`, following
  `ExprStmt::~ExprStmt` in `src/frontend/ast/ast.cpp`. So a node is destroyed without per-node
  recursion whether it is reached through a parent's worklist (function scope) or through its
  last `std::shared_ptr` (module item). An item owned through `std::shared_ptr` is never pushed
  onto a worklist, as is already true of `FunctionDecl`. `SymbolDecl` and `BooleanLiteral` have
  no children.
- **Load sequence** (`Module::load`, `src/runtime/evaluator/module.cpp`): lex, parse, validate,
  and create the module environment, as today. Then:
  1. **Register functions.** For each item in source order for which `asFunctionDecl` is
     non-null, bind its name to a new `Function(declaration, environment_)` with
     `BindingKind::Function`. All functions are bound before any initializer runs.
  2. **Run module-level initializers (DA1 a, §4.5.1).** For each `ConstDecl` or `SymbolDecl`
     item in source order, call `item->evaluate(context, environment_)`. This is the same
     `evaluate` that runs function-scope declarations. It binds the name in the module
     environment. A completion that is not `Normal` is an `InternalError`. No script function
     runs (DA1 b).
  3. Return the module.

  `Module::load`'s documented exceptions gain `RuntimeError`, raised by step 2 (exit 70 through
  the existing `PhiliosError` handler in `src/cli/cli.cpp`). As today, a throw destroys the
  partly built `Module`, whose destructor calls `release()`, so the module environment and its
  `Function` cycle are freed even when initialization fails. `runMain` and `src/cli/cli.cpp`
  do not change: `main` is looked up and called only after `Module::load` returns. Unit tests
  that load a module and evaluate in its environment therefore see initialized module-level
  constants and symbols.
- **Teardown** (`Module::release`, unchanged in order and in member declaration order
  `source_`, `program_`, `environment_`):
  1. `environment_->releaseBindings()` drops every module binding: each `Function` (which breaks
     the module environment → `Function` → module environment cycle, D3) and each module-level
     constant and symbol value.
  2. `program_.clear()` drops the last strong reference to every module item, unless something
     outside the module still holds a `Function`.
  3. `source_.clear()`. No AST node refers to the buffer (see "Name storage" above). A
     `Function` that is still held outside the module therefore keeps a complete, self-contained
     `FunctionDecl`. It also keeps its closure environment (the module environment, now with no
     bindings, D3). It can be inspected and called safely. A call whose body looks up a
     module-level name fails, because that environment binds nothing. `Identifier::evaluate` raises
     the existing `RuntimeError(UndefinedIdentifier)` at the identifier, as today, and never
     reads freed memory.

  `Module` stays non-copyable and non-movable. `source_` keeps its declaration position. The
  `Module` class comment is updated to say that only tokens, which live during `load`, view the
  buffer (T2).

  This plan adds no new reference cycle. Module-level constants and symbols hold only values
  (`Integer`, `String`, `Boolean`, `Symbol`, or `null`). A module-level constant can't hold a
  `Function` in this plan (DA1 b, OQ-20). If a later plan allows it, step 1 still drops it in
  the same swap.

#### 4.14.3 Binding Records and the `Environment` Interface (supports AD1)
In `src/runtime/environment/environment.hpp`:

```cpp
/// @brief What declared a binding (§4.13).
enum class BindingKind { Function, Parameter, Variable, Constant, Symbol };

/// @brief A binding's kind and declared type, copied out of the table.
struct BindingInfo {
    BindingKind kind;
    std::optional<DeclaredType> declaredType; ///< No value for BindingKind::Function.
};
```

- The table stores, for each name, the value, the `BindingKind`, and the declared type by value.
  It holds no AST pointer.
- `define(name, value)` keeps its signature and records `BindingKind::Function` with no declared
  type. Module function registration and the existing tests use it.
- A new overload `define(name, value, BindingKind kind, DeclaredType declaredType)` binds
  parameters (`callFunction`, with `Parameter` and the parameter's type), `let` variables
  (`Variable`), constants (`Constant`), and symbols (`Symbol`, with
  `DeclaredType{TypeName::Symbol, false}`). Its preconditions match `define`'s.
- `[[nodiscard]] std::optional<BindingInfo> bindingInfo(std::string_view name) const` searches
  this environment, then each enclosing scope, like `lookup`, and returns a copy.
- `void assign(std::string_view name, std::shared_ptr<Object> value, SourceLocation
  targetLocation)` performs §4.8 step 4 on the binding that `bindingInfo` would find. For a
  `Constant` whose current value is not `null`, it throws `RuntimeError(ConstantReassignment)` at
  @p targetLocation and stores nothing. For a `Function` or `Symbol` binding, or an unbound name,
  it throws `InternalError`. Otherwise it replaces the value. Strong guarantee. It never calls
  script code, and no reference into the table escapes.
- `AssignStmt::evaluate` (`src/runtime/evaluator/evaluate.cpp`) performs §4.8 with owning copies:
  1. `bindingInfo(target)`; absent is an `InternalError`. For a `Constant`, `lookup(target)`;
     a non-`null` value raises `ConstantReassignment` at the target.
  2. Evaluate the right-hand side.
  3. For a `Constant`, a `null` value raises `ConstantNullWrite` at the right-hand side. Then
     `matchesDeclaredType(value, *info.declaredType)` failing raises `AssignmentType` at the
     right-hand side.
  4. `environment->assign(target, value, targetLocation)`.

## 5. Errors
Diagnostics use the existing format `main.phil:<line>:<column>: <class> error: <message>`.
Messages are escaped as they are today. "First byte" means the first byte of the named token or
construct. Tests check the class, line, column, and exit status, and check message text only where
it is given in `code` below. Lexical, syntax, and declaration errors stop the program before it
runs, so stdout is empty. After a runtime error, output that earlier `echo` calls wrote stays on
stdout.

### 5.1 Lexical (exit 65)

## 6. Security and Resource Limits

### 6.1 Deeply Nested and Malformed Input
- **Nesting limit.** Expression operators count toward the existing parser nesting limit of 256
  (plan 0001 D7; `ExecutionContext::kMaxParseNesting`), together with blocks and argument lists
  (DA7). A `!` adds one level for its operand. Each `==` or `!=` in a chain adds one level, because
  a left-associative chain of *n* operators is a tree *n* levels deep. Reaching level 257 is a
  syntax error at the operator token that would open it, reported before any further nesting is
  built. A function body is level 1, so its expressions start at level 1. A module-level
  initializer is not inside a block, so its expression starts at level 0. This bounds the
  recursion depth of the validator, the evaluator, and every other AST walk by 256 plus a small
  constant.
- The parser reads an equality chain **iteratively**, using a counter and a loop rather than one
  C++ stack frame per operator, so that input with 100,000 operators fails with the syntax error
  and not with a stack overflow. Because `!!` is rejected at the second `!` (DA5), a run of `!`
  tokens never nests; deep `!` nesting is possible only through call argument lists, which already
  count toward the limit.
- New AST nodes take part in the existing iterative destruction protocol (`detachChildren`), so
  destroying a maximally nested expression does not recurse once per node.
- New statements in a body are stored in the existing statement vector. Many declarations
  (bounded by the 2 MiB source limit) cause no recursion.
- Malformed operator sequences (`===`, `!==`, `= =`, `!` at end of file) are rejected by maximal
  munch plus the grammar, never by reading past the token stream.

### 6.2 Numeric Edge Cases
- `Integer` equality compares the two `std::int64_t` values exactly, with no conversion or
  arithmetic, so `INT64_MIN == INT64_MIN` and `INT64_MAX != -1` raise no UB. No arithmetic is added
  (AGENTS.md Open Decisions: remaining numeric semantics stay open).

### 6.3 Object Lifetimes and Reentrancy
- Equality of `Function` and `Symbol` values compares object identity, the addresses of the
  owning `std::shared_ptr` targets, while both operands are held by owning copies. It never
  dereferences a released object.
- `String` equality compares lengths and then bytes. It is linear and does not recurse.
- Assignment holds owning copies of the evaluated value and of the target environment from step 1
  to step 4 (§4.8). Evaluating the right-hand side may run script code. For a constant, the store
  re-checks the null state (§4.8 step 4) as defense in depth, so that no write-once constant is
  written twice even if a later plan or a validator defect lets script code reach it. Environment
  lookups still return owning copies. No reference, pointer, or iterator into a binding table is
  held across evaluation.
- Module-level initialization runs no script functions (DA1 b), so it has no reentrancy: no
  script code can observe a partly initialized module environment.
- Module items and declaration ownership follow §4.14.2 (AD2): a `Function` shares its
  `FunctionDecl` with the `Program` through one control block, module-level `ConstDecl` and
  `SymbolDecl` nodes are referenced only by the `Program`, and no binding or runtime object
  points into the AST except a `Function`'s declaration. Module teardown keeps its current
  order, and a `RuntimeError` during module initialization still releases the module
  environment and its `Function` cycle through `~Module`.
- **Source-buffer lifetime (CERT MEM50; security review round 1).** AST nodes own their name
  text (§4.14.2, "Name storage"), so no AST node and no runtime object holds a view into the
  module's source buffer. Only tokens do, and tokens are local to `Module::load`. A `Function`
  retained after its `Module` is released or destroyed keeps a self-contained `FunctionDecl`:
  reading its declaration's names and calling it read only memory that the `Function` co-owns.
  This holds no matter when the source buffer is freed, so the fix doesn't depend on teardown
  order and adds no ownership edge. T3-ARCH-2 and T3-ARCH-8, run under ASan (T12), verify it.
- The evaluator performs every §4.10 runtime check unconditionally (§4.14.1, AD1), so a validator
  defect that wrongly accepts a site can't skip a runtime type check.
- Symbols are owned by the bindings and variables that hold them. Holding a symbol in a `Symbol`
  variable keeps it alive. A per-call symbol (DA4) returned through a `Symbol` value outlives its
  call environment through that owning reference.
- No `Boolean`, `Symbol`, or binding state is process-global or `static` (AGENTS.md Core
  Architectural Constraint 1). `true` and `false` are literal keywords, not global bindings
  (§4.2.2). Module-level constants and symbols live in the module's private environment.

### 6.4 Diagnostics, Files, and Imports
- Diagnostics copy and escape any script-derived text, as today. No new file handling, imports, or
  iteration-order exposure is added.

- T3-ARCH-1 (AD2 representation): parsing `const a: Integer = 1`, `function f(): Integer:` …,

  are `ConstDecl`, `FunctionDecl`, `SymbolDecl`, and `FunctionDecl`, in that order.

  expires when the test drops the `Function`. The ASan run (T12) reports no heap-use-after-free.
- T3-ARCH-8 (AD2, a retained `Function` is usable after its module is gone; security review
  round 1): load
  `function f(value: Integer): Integer:\n    let copy: Integer = value\n    return copy\nfunction g(): Integer:\n    return f(1)\nfunction main():\n    return f(1)\n`

  2. Check that `declaration()->name()` is `f`, that `params()[0]->name()` is `value`, and that

  3. Call `callFunction(context, f, {Integer 7}, callSite)`. `callSite` is a `CallExpr` built

  5. Calling the retained `g` after `module.reset()` raises `RuntimeError(UndefinedIdentifier)`

  6. After the test drops every retained `Function`, weak observers of the `FunctionDecl` and of

## 10. Open Questions

### 10.1 Answered by the developer on 2026-11-21 (recorded as DA1–DA7)
These were OQ-1 to OQ-14 and OQ-16 in revision 1. They are no longer open.
- **DA1 (was OQ-1), module-level declarations:** (a) initializers run once, in source order, after
  checking and before `main`; (b) a module-level initializer may contain only literals, `!`, `==`,
  `!=`, and earlier module constants and symbols, with no function calls; (c) functions may use
  module constants and symbols declared later in the file; (d) a function may not make the one
  write to a module-level nullable `const`, which is an error before execution. Applied in
  §4.5.1, §4.7, §4.8, §5.3, T6, T9, and §9.11.
- **DA2 (was OQ-2):** a parameter behaves like a `let` variable of its declared type and may be
  assigned. Applied in §4.8, §4.13, T6, T8, and T3-ASSIGN-7.
- **DA3 (was OQ-3), as corrected by the developer on 2026-11-21:** "A function's declarations and
  parameters may **not** reuse a name declared at module level." Shadowing is not allowed. This
  correction supersedes every earlier answer to OQ-3, including the "shadowing allowed" answer
  applied in revision 2. It keeps the plan 0001 D15 rule (a parameter can't share a module
  function's name) and generalizes it to all module-level names and to function-scope `let`,
  `const`, and `symbol` declarations. D19 still forbids duplicates within one scope. Applied in
  §3 C12, §4.5, §4.5.1, §4.8, §4.9, §4.10, §4.13, §5.3, §5.4, T6, T10, T11, AC-2, and §9.10.
- **DA4 (was OQ-4):** a function-scope `symbol` declaration creates a new symbol on every call.
  Applied in §4.9, §4.13, T9, and T3-SYM-7.
- **DA5 (was OQ-5):** `!!x` is not allowed, consistent with `!` being non-associative in the
  long-term table. Applied in §4.4, §4.11.1, §4.12, §5.2, §6.1, T3, T3-PARSE-10, and
  T3-NEST-2/3.
- **DA6 (was OQ-8):** a statically nullable value for a non-nullable `let` or assignment target
  is rejected before execution, to match D15. Applied in §4.10 rule 5, §5.3, T7, and T3-DECL-9.
- **DA7 (was OQ-9 to OQ-14 and OQ-16), defaults accepted:** `?Symbol` targets accept bare symbol
  names; existing call, return, and `echo` checks stay at runtime; no grouping parentheses; static
  type errors use the `declaration` class (exit 65); `!`, `==`, and `!=` count toward the nesting
  limit of 256; `echo(true)` and `echo(false)` are syntax errors; the plan is not split.
- OQ-6 and OQ-7 of revision 1 are settled by grill decisions D20 and D21.

### 10.3 Decided by the plan composer (architecture only, 2026-11-21)
The architecture review, round 1, asked the developer two questions (runtime-check metadata on
AST nodes or in a separate artifact, and the `FunctionDecl` ownership model after reshaping
`Program`). Both are internal architecture with no script-visible effect, and the current code
settles them, so the composer decided them instead of blocking. The developer may override
either one; doing so changes only §4.14, T2, T3, T6–T9, and §9.12.
- **AD1 (validator-to-evaluator contract):** neither AST fields nor a side table. The validator
  keeps `void validateProgram(const Program&)` and produces no artifact; the evaluator performs
  every §4.10 runtime check unconditionally, with expected types taken from the declaring node,
  the environment's binding record, or the fixed `Boolean` for `!` (§4.14.1, §4.14.3).
  *Rationale:* static soundness makes the unconditional check observably identical to checking
  only undecidable sites; it reuses the current `call.cpp` model and the single
  `matchesDeclaredType`; it keeps AST nodes immutable and shared with `Function` objects (D3);
  and a validator defect can't silently skip a check (security first).
- **AD2 (module items and declaration ownership):** `ModuleItem = std::shared_ptr<const ASTNode>`,
  `Program = std::vector<ModuleItem>`, and `asFunctionDecl` using `std::static_pointer_cast`, so
  a `Function` shares its `FunctionDecl`'s control block with the `Program` exactly as today.
  Module-level `ConstDecl` and `SymbolDecl` are owned only by the `Program`. `Module::load` runs
  module-level initializers after function registration; `Module::release` is unchanged
  (§4.14.2). *Rationale:* it keeps the current D3 ownership edge and teardown order unchanged,
  adds no cycle, keeps the existing `kind()`/`static_cast` dispatch convention, and leaves
  `Function`, `callFunction`, `runMain`, and the CLI unchanged.
- **AD2, name storage (added in revision 5 for security review round 1, 2026-11-21):** AST
  nodes own their name text as `std::string`, and no AST node holds a view into the source
  buffer (§4.14.2, "Name storage"). *Rationale:* security first. It removes the dangling-view
  hazard for every node that can outlive the `Module`, now and in later plans, without a
  lifetime rule to maintain. It adds no ownership edge or reference count. It changes no
  interface except that the `Identifier` and `Param` constructors may now throw
  `std::bad_alloc`. The rejected alternative was a shared, immutable
  `std::shared_ptr<const std::string>` buffer co-owned by each `FunctionDecl`. It would keep a
  rule that every future escaping node must follow, and it would change the `Parser`,
  `FunctionDecl`, and test-support interfaces. The cost of owned names is small: parse-time
  copies, and 8 to 16 bytes more per named node. Internal architecture only, with no script-visible
  effect. The developer may override it; doing so changes only §4.14.2, §6.3, T2, and
  T3-ARCH-2, T3-ARCH-8, and T3-ARCH-9.
