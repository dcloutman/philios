## 1. Summary
Build the first working Philios interpreter: a standalone native C++20 binary, `philios`, that
reads `main.phil` from the current directory and executes its `main()` function. This milestone
establishes the source loading → lexer → parser → declaration validation → evaluation pipeline, the
minimal object model (`Object`, `ImmutableObject`, `Integer`, `String`, `NullObject`, `Function`),
and the build, static-analysis, and test infrastructure that later plans build on. Per D4 it stays
one bootstrap plan, divided into milestones that each build and test independently.

## 2. Scope

### In scope
- CLI: `philios` with no arguments runs `./main.phil` (D19).
- Safe loading of `main.phil` (D21, D32).
- Lexer for the syntax subset in §3.3, with UTF-8 validation (D8, D23, D27, D28).
- Recursive-descent parser for the grammar in §3.4, with a nesting limit (D7).
- Call-depth and evaluation-depth limits in the evaluator (D7, D24).
- Whole-file declaration validation before anything executes.
- Object model (D1): `Object`, `ImmutableObject`, `Integer` (64-bit signed, D2), `String`,
  `NullObject` (D18), and `Function` (D16). There is no `RuntimeValue` variant.
- Function declarations with typed parameters and a typed return; calls; `return`; the `pass`
  statement (D11); the `null` literal (D18); functions as values (D16, absorbing only the functions-as-values part of plan 0005,
  "Functions are Objects").
- Exit statuses (D20, D30).
- Build: CMake, strict ISO C++20, `clang-tidy`, sanitizers, and doctest for tests (D9, D10).
- AGENTS.md updates for the Open Decisions this plan settles (§6).
- Source layout following `docs/developers/src/getting-started/directory-structure.md` (D41), with
  headers beside their sources, one include root `src/`, and test code only under `tests/` (D42–D45,
  §7.1), plus updates to that document and to the style guide's include rule, which is the
  `#pragma once` / include-order bullet under "Naming & Layout" (D46; the guide has no separate
  Includes section).

### Non-goals
- Variables, assignment, and module-level constants. Consequently no syntax in this plan can
  rebind a function name; D17 (function names are constants) is satisfied by the grammar plus D15.
- Arithmetic, comparison, unary minus, and negative literals (D22).
- Conditionals (`if` / `elseif` / `else`) and loops.
- The `List` type, script command-line arguments, and `main(args: List[String])` (D12).
- String concatenation (`.`) and `${...}` interpolation (`${` is reserved and rejected).
- `echo` and other output builtins. Scripts communicate only through the exit status.
- Plan 0005's functor and class sugar: `function` as shorthand for a `Function` subclass,
  `invoke()`, and extending function classes (D16 absorbs only functions as values).
- Modules, `import` / `export`, classes, interfaces, mixins. There is exactly one `Module`, for
  `main.phil`; no cross-file sharing exists.
- Anonymous functions, nested function declarations, and closures over local scopes (v0.1.0 per
  AGENTS.md).
- Function signature types such as `Function(String): String` (later plan); `Object` as a

- `philios.json` and a project-directory argument (D19, D35).
- Non-default indentation declarations.
- Signal handling: no interrupt flag; Ctrl-C has its default OS behavior.
- Lexer/parser fuzzing (its own plan, per AGENTS.md).
- Performance and binary-size targets (D34): nothing is measured, recorded, or enforced, and no
  benchmark or size check is a test or acceptance criterion. A later plan sets up benchmarks and
  targets.
- A startup stack-size check (`getrlimit`) or a dedicated large-stack evaluation thread (deferred
  by D24; no target plan; see §5.1).
- Reachability analysis beyond "no statement after `return` in the same block" (D29); it belongs
  to the control-flow plans.
- A platform-abstraction layer for file I/O (D32). Loading is POSIX only.
- Updating `docs/language_rules.md` with this plan's rules (D37; see §5.1).
- Platforms other than Linux x86-64 with GCC 13+ (other compilers best-effort, D9).

## 3. Specification

### 3.1 Entry point and CLI
- `philios` takes no arguments. If `argc > 1`, it reports a usage error and exits 64 (D19, D20).
  `argc` of 0 or 1 means no arguments.
- The project directory is always the process's current working directory. The interpreter loads
  `main.phil` from it (§3.2), then lexes, parses, and validates the **entire** file. Execution
  begins, by calling `main()`, only if every phase succeeds; a declaration error in a function that
  `main` never calls still prevents execution.
- On success the exit status is derived from `main`'s result (§3.8).
- `philios.json` is never opened, read, stat'ed, or checked. Whether it exists and what it contains
  have no effect (D35).
- `main.phil` is opened by relative name from the current directory, only by
  `src/cli/source_file.cpp` (§3.2, D32, D45).

### 3.2 Loading `main.phil` (D21)
- Open first, then check: open `main.phil` read-only without following a symbolic link in the
  final path component and without blocking on a FIFO, then inspect the **opened descriptor** and
  require a regular file. Never check a path and then open it.
- A symlinked `main.phil` is rejected even if its target is a regular file. Directories, FIFOs,
  sockets, and devices are rejected.
- Maximum source size is 2 MiB = 2,097,152 bytes, not configurable. A 2,097,152-byte file is
  accepted; a 2,097,153-byte file is rejected. The limit is enforced while reading, before the
  buffer grows: read in bounded chunks, never let the buffer exceed 2,097,152 bytes, and detect an
  oversized file by successfully reading any byte past the limit. A size reported by `fstat` may be
  used only as a reservation hint when it is ≤ the limit; it is never trusted as the bound.
- Any open, inspect, or read failure, including one after a partial read, is a startup error
  (exit 66). Nothing is lexed or executed after a startup error.
- An empty file loads successfully and then fails validation (no `main`).
- **POSIX loading sequence (D32).** The standard library cannot open without following symlinks or
  inspect an opened stream's file type, so `src/cli/source_file.cpp` calls, in order,
  `open("main.phil", O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC | O_NOCTTY)` (D32 as amended by
  D47), then `fstat` on the open descriptor (open first, then check, per D21), then `read` in
  bounded chunks (retried on `EINTR`), then `close`. An RAII class owns the descriptor and closes it
  on every exit path, including exceptions. The descriptor class deletes its copy and move
  operations, so no copy can close the same descriptor twice. No other file may call `open`,
  `fstat`, `read`, or `close` directly, and no other file includes `<fcntl.h>`, `<sys/fcntl.h>`,
  `<unistd.h>`, `<sys/unistd.h>`, or `<sys/stat.h>`; no file under `src/`, including
  `source_file.cpp`, includes `<sys/syscall.h>`. T-BUILD-6 checks the header rule mechanically. The
  call ban follows from it (without these headers the functions are not declared) and is otherwise
  enforced by code review; T-BUILD-6 does not scan for calls. There is no platform-abstraction
  layer (D9; AGENTS.md assumes POSIX). `O_NONBLOCK` ensures that opening or reading an empty FIFO
  cannot block. `O_NOCTTY` (D47) ensures that a terminal device named `main.phil` cannot become the
  process's controlling terminal before `fstat` rejects it.
- **Partial-read failure is testable: the read seam.** A read error cannot be produced reliably from
  a CLI test, so the bounded chunk-reading loop takes the chunk-read operation as a parameter. Its
  interface uses only project and standard-library types:
  - `src/cli/source_file.hpp` includes no POSIX header and mentions no file descriptor or POSIX
    type. It declares a result struct `ChunkReadResult` holding a `std::size_t` byte count and a
    `std::error_code` error, and the operation type
    `using ChunkReader = std::function<ChunkReadResult(std::span<char> destination)>`. A result
    with no error and 0 bytes means end of file; an error equal to `std::errc::interrupted` means
    "retry"; any other error means failure. A result that holds an error must report 0 bytes; a
    result with an error and a nonzero byte count is an `InternalError` (see below). The operation
    never reports through the global `errno`.
  - It declares the loop, `[[nodiscard]] std::string readBoundedSource(const ChunkReader& readChunk,
    std::size_t sizeHint)`, defined in `src/cli/source_file.cpp`, so the loop body (including the
    size check) is not in the header. `sizeHint` is used only to reserve capacity and only when it
    is ≤ the limit; 0 means no hint.
  - The loop is the **only** place that enforces the 2,097,152-byte limit, retries on
    `std::errc::interrupted`, and, on any failure (an error, an oversized file, a reported byte
    count larger than `destination.size()`, or an error reported together with a nonzero byte
    count, the last two being an `InternalError`), throws without returning or keeping any partial
    buffer. The size and I/O failures throw `StartupError`. The retry on
    `std::errc::interrupted` is deliberately unbounded: the shipped reader sees `EINTR` only when a
    signal with an installed handler interrupts `read`, this plan installs no handler, and so only
    signals sent from outside the process can cause a retry.
  - It declares the public entry point, `[[nodiscard]] std::string loadMainSource()`, which takes no
    read operation. It opens and checks `main.phil` as above and calls `readBoundedSource` with the
    only real reader: a lambda in an anonymous-namespace helper of `src/cli/source_file.cpp` that
    captures the RAII descriptor **by reference** (the descriptor is neither copyable nor movable),
    calls `read`, and converts `errno` into a `std::error_code` (`std::generic_category()`)
    immediately. Capturing by reference is safe (CERT EXP61) because the `ChunkReader` is a
    temporary passed to `readBoundedSource` and never outlives the descriptor, which is a local of
    `loadMainSource`.
  - Unit tests in `tests/unit/cli/` call `readBoundedSource` with fakes defined in the test file's
    anonymous namespace (D44): T-CLI-8 (partial read, `EINTR`, misreported results) and T-CLI-9
    (size boundary). The fakes call no POSIX function. No script can reach the seam, and the
    shipped binary passes only the POSIX reader. The terminal-device test T-CLI-10 (D47) calls
    `loadMainSource` itself in a forked child (§9).
- The loaded bytes are returned by `loadMainSource` as a `std::string` and moved into the
  `Module` before any view into them is created (§3.9). After that they are never mutated or moved.

### 3.3 Lexical structure

**Reading the input (bounds checks).** The lexer takes the source as a `std::string_view` and
reads bytes only through one private, bounds-checked accessor, for example
`[[nodiscard]] std::optional<unsigned char> peek(std::size_t offset) const noexcept`, which checks
that the current position plus `offset` (checked arithmetic) is less than the view's size and
returns no value at end of input. Every lookahead in the rules below (CR then LF, `/` then `/` or
`*`, `*` then `/`, `\` then the escape character, `$` then `{`, a digit then an identifier
character, and UTF-8 continuation bytes) goes through it. No other lexer code indexes the view or
dereferences an iterator into it. The UTF-8 functions in `src/frontend/lexer/utf8.hpp/.cpp` also
take a `std::string_view` and check every index before reading. The lexer never relies on a
terminator byte or spare capacity after the end of the buffer. T-LEX-12 checks this with
exact-size storage, so AddressSanitizer reports any over-read.

**Encoding and characters (D8, D23d, D23f, D28e).**
- The whole file must be well-formed UTF-8 (RFC 3629). Truncated sequences, stray continuation
  bytes, overlong encodings, surrogate code points (U+D800–U+DFFF), and code points above U+10FFFF
  are lexical errors wherever they occur, including inside strings and comments.
- Line and column numbers are 1-based. Columns count bytes, not characters. Each line break (see
  "Line breaks" below) adds 1 to the line number and resets the column to 1.
- NUL and every control character except tab (U+0009), LF (U+000A), and CR (U+000D) are lexical
  errors everywhere, including inside strings and comments. "Control character" means Unicode
  general category Cc: U+0000–U+001F, U+007F, and U+0080–U+009F.
- The Unicode bidirectional formatting characters U+202A–U+202E and U+2066–U+2069 are lexical
  errors everywhere, including inside strings and comments, to prevent "Trojan Source" spoofing
  (D28e). The error is at the character's first byte.
- Outside strings and comments, only ASCII is legal; any other character (including a UTF-8 BOM)
  is an unexpected-character lexical error.
- Tabs are allowed as whitespace between tokens and inside strings and comments. A tab in
  indentation is a lexical error.

**Line breaks (D28a).**
- LF, CR LF, and a lone CR (a CR not immediately followed by LF) each count as exactly one line
  break. `CR LF` is one break; `LF CR` is two breaks, so the line between them is blank. A file may
  mix the three styles freely. Elsewhere in this plan, "newline" and "line break" mean any of the
  three.
- A lone CR behaves exactly like LF everywhere: it ends a `//` comment; inside `/* */` it counts as
  a line for line numbers and for the multi-line comment rule; and it ends the physical line for
  the `;` continuation check (D23a) and the continuation rule below (D28c).
- Inside a string literal, any line break, including a lone CR, is a raw newline and therefore a
  lexical error (D23b).
- Accepting lone CR and mixed line endings is a developer-accepted risk (§5.1).

**Comments (D28b).**
- `//` begins a comment that runs to the next line break. It may begin anywhere after the
  indentation, including after code.
- `/* ... */` is a comment that may span lines. An unterminated `/*` is a lexical error at the `/*`.
  Comment markers inside a string literal are string content.
- A `/* ... */` comment that contains a line break (a multi-line comment) ends its logical line at
  the `/*`, as a `//` comment would; the code before the `/*` follows the normal continuation rule.
  On the line containing the closing `*/`, only whitespace and comments may follow the `*/`; code
  there is a lexical error at the code's first byte.
- **A comment separates tokens (D40).** A comment always ends the token before it and works like a
  space between tokens; it never joins the text on either side into one token. So
  `return/*c*/42` lexes as `return` `42`; `fo/*c*/o()` lexes as `fo` `o` `(` `)` and is a syntax
  error at `o`; and `12/*c*/abc` lexes as `12` `abc` (not the malformed-number error for `12abc`)
  and is a syntax error at `abc`. A comment never counts as indentation (see Indentation below).
  `;` continuation is unchanged: comments are still removed before the continuation check.

**Logical lines and continuation (D23a, D28c).**
- A newline terminates a statement. If, after comments and trailing whitespace are removed, a
  line's last character is `;`, the statement continues onto the next physical line: the `;` and
  the newline are discarded, no NEWLINE, INDENT, or DEDENT token is produced at the join, and the
  continuation line's leading whitespace is not indentation. `;` is a continuation marker, never a
  terminator.
- Comments are removed before the continuation check, so `foo(1,; // note` continues.
- A `;` anywhere else (mid-line, or a line consisting only of `;`) is a lexical error.
- A `;` continuation followed by end of file, a blank line, or a comment-only line is a lexical
  error at the `;` (D28c). The physical lines that a multi-line comment covers after its opening
  line contain only comment text, so a `;` followed directly by a multi-line comment is this error.

**Indentation.**
- Blocks are indented by exactly 4 spaces per level (`docs/language_rules.md`).
- Indentation is measured only at the start of a logical line. Blank and comment-only lines carry
  no indentation and produce no tokens.
- **Start-of-line comments (derived from D40).** A line's indentation is only the spaces before its
  first comment or token. Spaces after a comment are ordinary gaps between tokens, never
  indentation. So `/*c*/    return 1` has indentation 0: inside a function body it dedents to
  module level, and `return` is then a module-level statement, a syntax error at the `return`
  token (if it is the body's only line, the body is empty, which is the D11 error). `    /*c*/return 1` has indentation 4 and is a valid body line.
- Indentation that is not a multiple of 4, that increases by more than one level, or that dedents to
  a level that is not open is a lexical error. Indentation where no block opens (the previous logical
  line did not end a function header) is a syntax error.
- A final line without a trailing line break is accepted (D23e). At end of file the lexer emits a
  NEWLINE if one is pending and a DEDENT for every open level.

**Tokens.**
- Identifiers: `[A-Za-z_][A-Za-z0-9_]*`, case-sensitive.
- **Reserved words (D11, D16, D27).** Exactly these 23 words are reserved: `function`, `return`,
  `null`, `pass`, `Integer`, `String`, `Function`, `Object`, `ImmutableObject`, `NullObject`,
  `UnsignedInteger`, `Float`, `if`, `elseif`, `else`, `class`, `extends`, `implements`,
  `interface`, `mixin`, `with`, `export`, `import`. Matching is case-sensitive and whole-token, so
  `Integer2`, `integer`, and `_if` are ordinary identifiers. The lexer emits a reserved word as a
  keyword token, never as an identifier. Only the first seven have a meaning in this plan's
  grammar; the others are reserved for later features. A reserved word where the grammar requires
  an identifier (a function name, a parameter name, or an identifier expression or callee) is a
  syntax error at the word's first byte (§3.4, §4).
- Punctuation: `(` `)` `:` `,`. Any other character outside strings and comments, including `-`,
  is an unexpected-character lexical error.
- Integer literals: decimal digits only. The value must fit in a signed 64-bit integer; a literal
  greater than 9,223,372,036,854,775,807 is a lexical error, never wrapped. The conversion lives
  in the frontend, not in the runtime object model: `[[nodiscard]] std::optional<std::int64_t>
  parseDecimalInteger(std::string_view digits) noexcept` in
  `src/frontend/lexer/integer_literal.hpp/.cpp` parses with `std::from_chars`, requires full
  consumption, and handles `result_out_of_range` by returning no value (out of range is its only
  failure, because the lexer has already checked the digits and the leading-zero rule). The lexer
  raises the located `LexicalError`; the integer token carries the `std::int64_t` value. A digit
  sequence immediately followed by an identifier character (e.g. `12abc`) is a lexical error; a
  comment between them separates the tokens instead (D40). Negative
  literals are deferred with arithmetic (D22), so `INT64_MIN` cannot be written yet; this is a
  documented limitation. A literal with a leading zero other than `0` itself (for example `007` or
  `00`) is a lexical error at the literal's first byte (D28d).
- String literals: double-quoted. Escapes are exactly `\\`, `\"`, `\n`, `\t`; any other escape is a
  lexical error (D23c). A raw line break (LF, CR LF, or lone CR) inside a string is a lexical error
  (D23b, D28a), as is end of file before the closing quote. The sequence `${` inside a string is
  reserved and is a lexical error. The literal's value is the escape-processed bytes, stored in an
  owned `std::string`.
- **A `\` at the end of a line or of the file.** A `\` starts an escape only when another
  character follows it on the same line. A `\` followed by end of file is the unterminated-string
  error, reported at the opening `"` (as for any end of file before the closing quote). A `\`
  followed by a line break (LF, CR LF, or lone CR) is the raw-line-break error, reported at the
  line break's first byte (the LF or the CR), which is the column right after the `\` (D23b,
  D28a: every line break inside a string is a raw newline). The unknown-escape error at the
  backslash applies only when a character other than `\`, `"`, `n`, or `t` follows the `\` on the
  same line. T-LEX-9 and T-LEX-12 test these cases.

### 3.4 Grammar
Only these productions are legal; anything else is a syntax error. `NEWLINE`, `INDENT`, and
`DEDENT` are produced by the lexer at logical-line boundaries (§3.3). In the notation, `{ }` means
zero or more and `[ ]` means optional.

```
program     := { funcDecl }                        (module level: declarations only)
funcDecl    := 'function' IDENT '(' [ params ] ')' [ ':' typeName ] ':' NEWLINE block
params      := param { ',' param }                 (no trailing comma)
param       := IDENT ':' typeName
typeName    := 'Integer' | 'String' | 'Function' | 'null'
block       := INDENT stmt { stmt } DEDENT          (at least one statement, D11)
stmt        := returnStmt | passStmt | exprStmt
returnStmt  := 'return' [ expr ] NEWLINE
passStmt    := 'pass' NEWLINE
exprStmt    := callExpr NEWLINE                    (result discarded)
expr        := INTEGER | STRING | 'null' | IDENT | callExpr
callExpr    := IDENT '(' [ args ] ')'
args        := expr { ',' expr }                   (no trailing comma)
```

- `pass` is a no-op statement allowed anywhere a statement is (D11). Every block must contain at
  least one statement; an empty block, or one containing only blank and comment lines, is a syntax
  error. Write `pass` for an intentionally empty body.
- Module level contains only function declarations: a `return`, `pass`, or expression statement
  written at module level is a syntax error. Statements belong only inside function bodies.
  Function declarations belong only at module level: a `function` declaration inside a function
  body is a syntax error.
- The callee of a call is always an identifier; calling a call result (`f()()`) is a syntax error.
- Only an expression statement that is a call is allowed; a bare literal, `null`, or identifier as
  a statement is a syntax error.
- `IDENT` never matches a reserved word (§3.3). A reserved word in an `IDENT` position (function
  name, parameter name, identifier expression, or callee) is a syntax error at the word (D27).
- **Nesting limit (D7):** the parser keeps one nesting counter, incremented on entering a block and
  on entering a call's argument list, and decremented on leaving them. A function body is nesting
  level 1, so `main`'s `return f(g(1))` reaches level 3. Reaching level 257 is a syntax error at the
  token that would open the 257th level, reported **before** recursing further. The limit is the
  named constant `kMaxParseNesting = 256`, a `static constexpr` member of the execution context
  (AGENTS.md: limits are named constants held by the execution context). The parser does not take
  the execution context, because it runs no Philios code: it receives the limit as a value (a
  `std::size_t maxNesting` argument of the parser's constructor or entry function, declared in
  `src/frontend/parser/parser.hpp`). `Module::load`, and before task 7 the interim pipeline in
  `runProject`, pass `ExecutionContext::kMaxParseNesting` (§3.9).

### 3.5 Functions and declarations
Whole-file validation runs after parsing and before anything executes. Every rule in this section
is checked in every function, including functions that are never called. Each violation is a
declaration error (exit 65) at the location given in §4.

- Every function except `main` must declare a return type (`typeName`). A function that returns
  nothing declares `null`, e.g. `function foo (bar: String): null:`.
- Function names are unique within the module; a duplicate is a declaration error. Declarations may
  appear in any order; forward references and direct and mutual recursion are permitted (subject to
  the call-depth and evaluation-depth limits, §3.7).
- Parameter names are unique within a function (duplicate: declaration error) and may not equal the
  name of any module function, including `main` (D15).
- A declared function name is a constant (D17): nothing in this plan can rebind it.
- **`main` (D12, D25):** exactly one function named `main` must exist (none is a declaration error;
  two is the duplicate-name error). It has zero parameters. Its return annotation is omitted or
  `Integer`; any other annotation is a declaration error. Its return type is always `Integer`. A
  bare `return` in `main` is a declaration error. The identifier `main` may appear only as the name
  in its own declaration. Any other use is a declaration error at the identifier: a call such as
  `main()` (from any function, including `main` itself), and a value reference such as
  `apply(main, 1)` or `return main`. A parameter named `main` is already rejected by D15, so this
  check needs no scope analysis.
- **Return requirements (D13, D26):**
  - A non-`main` function whose return type is not `null` must execute `return <expr>`. Falling off
    the end of its body is a runtime error. A bare `return` in such a function is a declaration
    error at the `return` keyword (D26).
  - A `null`-returning function may use bare `return`, `return null`, or fall off the end; each
    returns `null`.
  - `main` returns `Integer` 0 if its body completes without executing `return`; this is the only
    exception to the rule above.
- **No statements after `return` (D5, D29):** `return` ends the function immediately (D5). Any
  statement that follows a `return` in the same block, including `pass`, is a declaration error at
  the first such statement. This applies after bare `return`, `return null`, and `return <expr>`.
  Blank and comment-only lines after a `return` produce no statements and are allowed. Only the
  same block is checked (in this plan every block is a function body); full reachability analysis
  belongs to the control-flow plans.
- **Undefined identifiers (D31a):** every identifier used as a value or as a callee must name a
  parameter of its enclosing function or a module-level function declared anywhere in the file
  (forward references are allowed). Otherwise it is a declaration error at the identifier. The
  identifier `main` is governed by D25 above. There are no block scopes (D15).

### 3.6 Values, names, and types
- **Everything is an object (D1).** Every runtime value is a `std::shared_ptr` to an `Object`.
  `Integer` and `String` are `ImmutableObject` subclasses whose storage (`std::int64_t`,
  `std::string`) is private to the class. `NullObject` and `Function` derive from `Object`.
  A value pointer is never `nullptr`; Philios `null` is the `NullObject` instance.
- **`null` (D18):** `null` is the single `NullObject` instance of the execution context (one per
  context, never process-wide). The `null` literal is an expression usable anywhere an expression
  is, including as an argument and a return value.
- **Functions as values (D16):** every declared function is exactly one `Function` object, created
  when the module is loaded. A function name used without parentheses evaluates to a reference to
  that object (not a copy, not a call). Function values can be passed as arguments and returned;
  parameter and return types use the untyped `Function` type. A `Function`-typed parameter can be
  called by its name.
- **Name resolution:** an identifier, as a value or as a callee, resolves first in the call's
  local environment (parameters), then in the module environment (functions). D15 keeps the two
  disjoint. Validation (D31a, §3.5) guarantees that every identifier in a validated module
  resolves. The evaluator still checks every lookup: an unresolved name is a runtime error (exit
  70) at the identifier, with the undefined-identifier runtime message class, and never falls back
  to anything else (no global fallback, AGENTS.md Core Architectural Constraint 1). Valid source
  cannot reach this check; keeping it a runtime error rather than an internal error is a
  developer-accepted choice (D31b, §5.1).
- **Exact typing (D14):** an argument or return value matches a declared type only if its runtime
  class is exactly that type: `Integer` ↔ `Integer` object, `String` ↔ `String` object, `Function`
  ↔ `Function` object, `null` ↔ the `NullObject`. There is no implicit conversion. In particular
  `null` matches only `null`-typed parameters and returns, and a `String` is never converted to a
  function or callable.
- **One type check.** `Object` exposes a pure virtual `[[nodiscard]] ObjectType objectType() const
  noexcept`, where `enum class ObjectType { Integer, String, Null, Function }` is declared in
  `src/runtime/object_model/object.hpp` and each `final` class returns its own tag. The comparison of
  a value with a declared `typeName` exists in exactly one function,
  `[[nodiscard]] bool matchesDeclaredType(const Object& value, TypeName declared) noexcept` in
  `src/runtime/evaluator/type_check.hpp/.cpp` (`TypeName` is the parsed `typeName` enumeration
  declared in `src/frontend/ast/ast.hpp`), and both the argument check and the return check
  call it. The "callee is a `Function`" check (§3.7) uses the same tag. No other code uses
  `dynamic_cast` or `typeid` to decide a Philios type.

### 3.7 Calls
- **Evaluation order (D6):** for `callee(a1, …, an)`: resolve the callee; then evaluate the
  arguments strictly left to right, each fully (including any calls inside it) before the next;
  then check the callee is a `Function`; then check the argument count; then check each argument's
  type left to right; then bind and run. The C++ evaluator evaluates each argument into a named
  local in a separate statement (CERT EXP50).
- Calling a value that is not a `Function` is a runtime error, detected at call time (D14, D16).
- Argument count mismatch and argument type mismatch are runtime errors (D14), checked at call time
  for direct calls and calls through `Function` parameters alike (D16).
- Each call creates a fresh local `Environment` holding the parameters, whose `enclosingScope` is
  the function's `closureEnv` (the module environment).
- The return value's type is checked against the declared return type when the function returns
  (D14); a mismatch is a runtime error. For `main`, a non-`Integer` result is that same error.
- The result of a call used as a statement is discarded, whatever its type.
- **Call-depth limit (D7):** the execution context counts active Philios calls; `main` is depth 1.
  A call that would make the depth exceed `kMaxCallDepth = 1000` is a runtime error raised before
  the callee's body starts. The counter is maintained by an RAII guard so it is restored on
  exceptions.
- **Where the call sequence lives.** The call sequence above (call-depth guard, callee-kind,
  arity, and argument-type checks, the fresh `Environment`, running the body, and the return-type
  check) is one function in `src/runtime/evaluator/call.hpp/.cpp`, for example
  `[[nodiscard]] std::shared_ptr<Object> callFunction(ExecutionContext&, …)`. `Function` in
  `src/runtime/object_model/` only holds its declaration and its `closureEnv`; it contains no call
  logic, so `runtime/object_model/` does not depend on `runtime/evaluator/`.
- **Evaluation-depth limit (D24):** the execution context also counts active
  `ASTNode::evaluate()` calls. Every entry to `evaluate()` on any node (blocks, statements, and
  expressions alike, so expressions and the call frames they start share one count) is counted by
  an RAII guard. The guard's check is the first thing `evaluate()` does, before any other work. An
  entry that would make the count exceed `kMaxEvalDepth = 10,000` is a runtime error (exit 70) at
  the line and column of the node being entered, with its own message class,
  `evaluation nested too deeply (limit 10000)`. The guard's constructor takes the execution context
  and the entered node's `SourceLocation` (the type from `src/common/errors.hpp`, task 2), not the
  node itself, so the guard and its unit test (T-SEC-5, task 3) need no AST node. The guard restores
  the count on every exit path,
  including exceptions. The value is fixed, not configurable, and held by the execution context.
  This bounds the evaluator's native recursion, which parser nesting and call depth together do not
  (§5).
- **Limit precedence (D24):** if both limits would trip, the call-depth error is reported. In this
  plan that case arises only when the evaluation-depth check fails on entry to a call expression
  while the current call depth already equals `kMaxCallDepth`, so the call, if made, would also
  exceed the call-depth limit. The call-depth error is then reported at the callee identifier
  instead of the evaluation-depth error. D5 and D7 are otherwise unchanged. The rule predicts the
  call-depth overflow before callee resolution, argument evaluation, and type and arity checks, so
  in that rare case it can hide a non-`Function` callee or argument-count error; both paths exit 70
  (D39).

### 3.8 Exit status (D20)
- Success: the status is `main`'s `Integer` result modulo 256, computed explicitly so that negative
  values map correctly: `r = v % 256; if (r < 0) r += 256;` (no overflow is possible; −1 → 255,
  `INT64_MIN` → 0, 300 → 44). The computation lives in `Integer` so its storage stays private.
- Interpreter failures use BSD `sysexits` values: usage 64; lexical, syntax, and declaration 65;
  missing or unreadable `main.phil` 66; runtime 70; internal 70. Out of memory (`std::bad_alloc`)
  and any other unexpected exception that reaches the top-level handler also exit 70
  (`EX_SOFTWARE`, not 71) (D30, §4). Collisions with script statuses are accepted; stderr
  distinguishes them (a successful script writes nothing to stderr).

### 3.9 Runtime architecture
- **Execution context:** owns the `NullObject` instance, the limit constants
  (`kMaxParseNesting = 256`, `kMaxCallDepth = 1000`, `kMaxEvalDepth = 10000`, each a
  `static constexpr` member), the current call depth, and the current evaluation depth, each with
  its RAII guard. It is created by the CLI entry point, passed explicitly by reference to
  `Module::load` and to every reentrant function, and is never global. The parser does not receive
  it; it receives only the value of `kMaxParseNesting` (§3.4).
- **Evaluation (D5):** every AST node derives from `ASTNode`, which provides a virtual
  `[[nodiscard]] Completion evaluate(ExecutionContext&, const std::shared_ptr<Environment>&) const`.
  `Completion` holds a kind (`Normal` or `Return`) and a non-null `std::shared_ptr<Object>` value.
  Expressions always complete `Normal` with their value. A `return` completes `Return`; a block
  stops at the first `Return` completion. No exceptions are used for control flow; exceptions carry
  only errors.
- **Where `evaluate` lives (D45).** The virtual `evaluate` is declared in
  `src/frontend/ast/ast.hpp` using forward declarations of `ExecutionContext`, `Environment`, and
  `Completion`, so the AST headers include no runtime header. Every definition of `evaluate` for the
  concrete nodes is in `src/runtime/evaluator/evaluate.cpp`. Task 6 creates that file with bodies
  that throw `InternalError` ("not yet implemented"); task 8 replaces them. `ASTNode`'s interface
  does not change between milestones.
- **Node kinds.** `src/frontend/ast/ast.hpp` declares `enum class NodeKind` with one value per
  concrete node class (§8 task 6) and a pure virtual `[[nodiscard]] NodeKind kind() const noexcept`.
  The validator identifies nodes with `kind()` and a `static_cast` to the matching `final` class.
  There is no generic visitor framework. Only the validator downcasts by kind; the evaluator and
  destruction use virtual dispatch only. The validator's `switch` over `NodeKind` handles every
  enumerator explicitly and has no `default` case that casts; a value it does not handle raises
  `InternalError` without casting. Test-only `ASTNode` subclasses (T-FN-6) are never passed to the
  validator: tests that use them call `evaluate` directly.
- **Argument nodes.** `CallExpr` holds its callee identifier and its arguments as owning pointers to
  `ASTNode`, the expression base, and its constructor accepts any `ASTNode`. This lets unit tests
  build calls from test-only `ASTNode` subclasses (T-FN-6, T-DECL-8).
- **Literal values.** An `IntegerLiteral` or `StringLiteral` stores its parsed value (an
  `std::int64_t` or an owned `std::string`) and creates a new `Integer` or `String` object each time
  it is evaluated. Caching one object per literal would make `frontend/ast/` depend on
  `runtime/object_model/`, which D45 avoids, and performance is a non-goal (D34); a later plan may
  revisit it.
- **Module:** owns, in this declaration order, the source buffer (`std::string`, never mutated after
  loading), the AST, and the module `Environment`. A `Module` is returned to the caller only after
  lexing, parsing, validation, and function registration all succeed; a module that fails to load is
  never visible.
- **The load pipeline and the buffer's lifetime.** One function runs the pipeline:
  `[[nodiscard]] static std::unique_ptr<Module> Module::load(ExecutionContext&, std::string source)`
  in `src/runtime/evaluator/module.hpp/.cpp`. It first allocates the `Module` on the heap with
  `std::make_unique` and moves `source` into the `Module`'s buffer member. The constructor is public
  but takes a passkey, a private nested type of `Module` that only `Module` can construct, so only
  `Module::load` can create a `Module` while `std::make_unique` (style guide) still works. Only then
  does it lex, parse,
  validate, and register functions, in that order, so every token and AST view is created into the
  buffer's final owner. If any phase throws, the `unique_ptr` destroys the partly built `Module` and
  nothing is returned. `Module` deletes its copy and move constructors and assignments, so neither it
  nor its buffer ever moves. `runProject` in `src/cli/cli.cpp` calls `loadMainSource` (§3.2), then
  `Module::load`, then the interpreter (task 8). Before task 7, tasks 4–6 use an interim pipeline in
  `runProject` that holds the source in a local `const std::string` that is never moved or reassigned
  while any token or AST node exists, and all of them are destroyed before `runProject` returns;
  task 7 replaces that interim code with the single call to `Module::load`.
- **Ownership and teardown (D3):** each `Function` holds a `std::shared_ptr<const FunctionDecl>`
  (shared with the module's AST) and a **strong** `std::shared_ptr<Environment>` `closureEnv` (the
  module environment). The module environment owns its `Function`s, forming the cycle
  module env → function → module env. No edge is weakened. The `Module` destructor (and an explicit
  `Module::release()` the execution root calls, safe to call twice) breaks the cycle
  deterministically by swapping the environment's table with an empty local and destroying the
  local, so no entry is destroyed while the table is being modified. Then the AST is released, and
  the source buffer last. Both are `noexcept` and allocate nothing (see "Iterative, non-throwing,
  non-allocating destruction" below).
- **Source views:** tokens and AST nodes may hold `std::string_view`s into the module's source
  buffer. No view, `Function`, or AST node may outlive the `Module`: the only value that leaves
  execution is `main`'s result, which is converted to an `int` status before teardown, and error
  objects copy any text and location they report.
- **Iterative, non-throwing, non-allocating destruction:** AST and environment destructors do not
  recurse once per node (style guide). Every AST, `Environment`, and `Module` destructor, the AST
  child-detach member, and `Module::release()` are `noexcept`, and none of them allocates memory,
  so destruction cannot fail or call `std::terminate` while unwinding from `std::bad_alloc` (CERT
  DCL57, D30). The strategy:
  - **AST:** the worklist is intrusive. Each `ASTNode` has a private
    `std::unique_ptr<ASTNode>` link member used only during destruction, and a virtual
    `void detachChildren(std::unique_ptr<ASTNode>& worklistHead) noexcept` member that moves each
    child the node owns through a `std::unique_ptr` onto the front of the list through the link
    member (moving `std::unique_ptr`s and clearing child vectors never allocates). Each concrete
    node's destructor moves its own children onto a local list head directly (it does not make a
    virtual call on the object being destroyed, CERT OOP50) and then calls one non-virtual
    `noexcept` helper that repeatedly takes the head node off the list, calls that node's
    `detachChildren` (a virtual call on a different, fully alive node), and destroys it, which is
    now childless and so does not recurse. **Unlink invariant:** a node's link member is always
    empty when the node is destroyed, because the link is itself an owning `std::unique_ptr` and a
    set link would destroy the next node from inside this node's destructor, bringing back
    per-node recursion through the list. The helper therefore moves the head out and then moves
    that node's link into the head before anything else
    (`node = std::move(head); head = std::move(node->link_);`), and only then calls
    `detachChildren` and destroys `node`. `detachChildren` pushes a child by moving the current
    head into the child's (empty) link and the child into the head. `FunctionDecl`s, which are owned through
    `std::shared_ptr` (shared with `Function`, D3), are never put on the list; each runs the same
    loop over its own children when its last owner releases it. A node of any class, including a
    test-only subclass with no children (whose `detachChildren` does nothing), is destroyed
    correctly.
  - **Environment:** an `Environment` destructor unlinks its `enclosingScope` chain in a loop
    (moving each `std::shared_ptr` link out before the node holding it is released, while the next
    node has no other owner), so no worklist container is needed.
  - **Module:** the destructor and `Module::release()` break the D3 cycle by swapping the module
    environment's table with an empty local table (a non-throwing operation on the supported
    toolchain, D9) and letting the local go out of scope, then release the AST and the buffer.
  T-OWN-4 and T-OWN-5 test this. No allocation-failure injection test is built: by construction
  destruction performs no allocation, and injecting allocation failure would need a replaced global
  `operator new` with mutable global state, which the style guide forbids.
- **Reentrancy (style guide):** every function that can run Philios code takes the execution
  context as a parameter. A call holds owning `std::shared_ptr` copies of the callee and every
  argument for the entire call. Environment lookups return an owning copy; no reference, pointer,
  iterator, or view into an environment table is held across a reentrant call.
- **Copy, move, and polymorphic bases:** `ASTNode`, `Object`, and `Module` delete copy and move; `ASTNode` and
  `Object` have public virtual destructors, and concrete classes are `final`.

## 4. Errors
Every language error is an exception derived from one Philios error base that carries a source
location (style guide). Host I/O failures, internal invariant failures, and resource exhaustion are
distinct types. In this plan "resource exhaustion" means `std::bad_alloc` only; the call-depth and
evaluation-depth limits are language runtime errors (`RuntimeError` kinds, class `runtime`, exit 70)
per D7 and D24, not a separate type. Error types derive from `std::runtime_error` so copying cannot
throw (CERT ERR60). The error types live in `src/common/errors.hpp/.cpp` (D45).
`RuntimeError` carries a distinct kind for each runtime condition in the table below, so tests can
tell, for example, call-depth from evaluation-depth errors.

**Top-level handler (D30).** `philios::runTopLevel` in `src/cli/cli.cpp` runs a body callable (in
the shipped binary, the whole CLI run) and catches, in order, the Philios error base, the startup
(host I/O) error, the internal error, `std::bad_alloc`, other `std::exception`s, and `catch (...)`,
all by `const&` where applicable. It reports each and returns the status below (CERT ERR51, ERR54,
ERR61). Its body uses the same non-template callable form as the read seam (§3.2):
`[[nodiscard]] int runTopLevel(const std::function<int()>& body)`, where the body returns the exit
status, so the handler's code stays in `src/cli/cli.cpp`. `main` in `src/main.cpp` calls it and adds
a last-resort `catch (...)` that returns 70, so no exception escapes `main()`. Nothing under `src/`
calls `std::terminate`, `assert`, `abort`, `exit`, `_exit`, or `_Exit` (CERT ERR50). The only use
of `_exit` in the project is the test-only exception for the T-CLI-10 forked child (§7). The out-of-memory report is a fixed
string literal written without allocating (no `std::string` construction or formatting). Tests
inject throwing bodies only from `tests/unit/cli/` (D44); the shipped binary contains no hook that a
script can reach.

Diagnostics go to stderr, one per failure (the first error stops processing). Nothing is ever
written to stdout. Formats:
- Located errors: `main.phil:<line>:<column>: <class> error: <message>`
- Startup: `philios: startup error: main.phil: <reason>`
- Usage: `philios: usage error: philios takes no arguments` followed by `usage: philios`
- Internal invariant failure: `philios: internal error: <message>`
- Out of memory (D30): `philios: internal error: out of memory`
- Any other unexpected exception (D30): `philios: internal error: unexpected exception`

`<class>` is one of `lexical`, `syntax`, `declaration`, `runtime`. Exact message prose is not
specified; tests match the prefix, class, line, and column. Three messages also have a normative
phrase that tests match: the evaluation-depth error contains `evaluation nested too deeply` (D24),
and the two D30 messages above are fixed. The location is that of the first byte
of the offending token or construct, as listed below. Control characters (including CR) and
terminal escape sequences in any echoed text are escaped, and script-derived text is never used as
a format string.

## 5. Security and resource limits
Priorities follow AGENTS.md: no input may crash the interpreter or cause undefined behavior.

| Limit | Value | Enforced | On violation |
|---|---|---|---|
| Source size | 2,097,152 bytes, not configurable (D21) | While reading, before the buffer grows | startup error, 66 |
| Parser nesting (blocks + call argument lists) | 256, `kMaxParseNesting` (D7) | Before recursing | syntax error, 65 |
| Call depth | 1,000, `kMaxCallDepth` (D7) | Before entering the callee body | runtime error, 70 |
| Evaluation depth (nested `evaluate()` entries) | 10,000, `kMaxEvalDepth`, fixed (D24) | First action of every `evaluate()` | runtime error, 70 |

- **Bounded structures.** Token count, AST size, and identifier and string lengths are bounded
  linearly by the 2 MiB source cap, so no separate count limits are added. All size arithmetic is
  checked (style guide).
- **Native stack (D24).** Parser nesting (256) and call depth (1,000) bound the parser and the
  number of Philios frames separately, but not their product: a function body can nest calls 255
  levels deep with a recursive call innermost, which without a further limit reaches about 255,000
  nested C++ `evaluate` frames. `kMaxEvalDepth = 10,000` bounds the number of nested `evaluate()`
  calls however nesting and calls combine, so the evaluator's native recursion depth is bounded by
  a constant. The plan assumes the Linux default main-thread stack of 8 MiB (`ulimit -s` = 8192).
  T-SEC-4 must pass under AddressSanitizer and in a release build on that default stack. If it
  fails at 10,000, the implementer stops and asks the developer; the value is not changed during
  implementation. T-SEC-1 (call depth 1,000) must still pass, so ordinary call chains reach the
  call-depth limit before the evaluation-depth limit. Running with a lower `ulimit -s` is a
  developer-accepted risk (§5.1).
- **Validator and destruction recursion** are bounded by the parser nesting limit; AST and
  environment destruction is iterative, `noexcept`, and allocates nothing, so unwinding from
  `std::bad_alloc` cannot terminate the process (§3.9, T-OWN-5).
- **Malformed input** (§3.3) is rejected with a located lexical error; the lexer never reads past
  the buffer: it reads only through one bounds-checked accessor over a `std::string_view` and
  validates every index (style guide), and T-LEX-12 runs every end-of-input lookahead on exact-size
  storage under ASan. Undefined names, misuse of `main`, and dead
  statements after `return` are rejected before execution (§3.5), even in functions never called.
- **CPU time** is not bounded: a program whose functions each call themselves twice runs
  exponentially long within the call-depth limit. This is accepted under the AGENTS.md interim trust
  model (scripts are trusted like `python`/`php` CLI scripts); Ctrl-C terminates the process with
  default OS behavior. Executing untrusted source is **not** sandboxed; do not run unknown `.phil`
  files with elevated privileges.
- **Memory:** live objects are bounded by the source size and call depth; `std::bad_alloc` is
  caught by the top-level handler and reported without allocating (§4, D30).
- **Numeric edge cases:** integer literals are parsed by the frontend's `parseDecimalInteger`
  (`std::from_chars`, §3.3) and range-checked;
  out-of-range literals are errors, never wrapped. There is no arithmetic in this plan. The exit
  status modulo uses `%` on `std::int64_t` with divisor 256, which cannot overflow. Any future
  wrapping arithmetic must use the style guide's centralized unsigned-arithmetic helpers.
- **Object lifetimes and reentrancy:** §3.9. Teardown is verified under AddressSanitizer and
  LeakSanitizer on normal completion and on unwinding after every error class.
- **File handling:** §3.2 (open-then-check, no symlinks, no blocking on FIFOs, `O_CLOEXEC`,
  `O_NOCTTY` so a terminal device cannot become the controlling terminal before it is rejected
  (D47, T-CLI-10), bounded read, a non-copyable, non-movable RAII descriptor, POSIX calls and POSIX
  headers confined to `src/cli/source_file.cpp`, D32,
  D45, with the header rule checked by T-BUILD-6; size limit, `EINTR` retry, and partial-buffer discard enforced only in
  the one read loop that both the shipped binary and T-CLI-8/T-CLI-9 exercise). Only `main.phil` in
  the current directory is ever opened; `philios.json` is never touched (D35); there are no imports.
- **Diagnostics:** control characters (including CR) and terminal escape sequences in echoed text
  are escaped; script text is never a format string.
- **Concurrency:** single-threaded (AGENTS.md interim default).

## 7. Build and verification
- Build: CMake, C++20, STL + header-only only (no ANTLR/Flex/Bison), single native binary.
  "Standalone" means no separate interpreter runtime dependency; the binary may link the system C
  and C++ runtime libraries dynamically.
- Language standard: ISO C++20 for all project targets, including tests. Set
  `CMAKE_CXX_STANDARD 20`, `CMAKE_CXX_STANDARD_REQUIRED ON` (fail rather than fall back to an older
  standard), and `CMAKE_CXX_EXTENSIONS OFF` (`-std=c++20`, not `-std=gnu++20`). Do not use
  compiler-specific language extensions.
- Toolchain (D9): GCC 13+ on Linux x86-64 (WSL Ubuntu 24.04), `clang-tidy` 18+. Other compilers are
  best-effort. CMake (D33): `cmake_minimum_required(VERSION 3.28)`, the version Ubuntu 24.04
  packages. There is no version range, the build uses no CMake feature newer than 3.28, and the
  commands below must work with CMake 3.28.
- Prerequisites (Ubuntu 24.04): `cmake`, a C++20 compiler, and `clang-tidy` 18 or later
  (`sudo apt install cmake clang-tidy`).
- Warnings: all project targets compile with `-Wall -Wextra -Wpedantic -Wconversion -Wshadow`, and
  the build must be warning-free. The doctest header is added as a `SYSTEM` include directory so its
  internals do not produce warnings.
- Layout: a static library `philios_core` (every `.cpp` file under `src/`, in all subdirectories,
  except `src/main.cpp`), the executable `philios` (`src/main.cpp` + `philios_core`), and the test
  executable `philios_tests` (the `.cpp` files under `tests/unit/`, including `tests/unit/support/`,
  + `philios_core` + doctest). `philios` never compiles or links test code or doctest, and never
  gets a `tests/` include path (D44). Directory placement and include paths: §7.1.
- Tests (D10): doctest, vendored as the single header `third_party/doctest/doctest.h` at a pinned
  release with its MIT `LICENSE` file beside it, used only by tests and driven by `ctest`. Unit
  tests cover each component. CLI golden tests run the real binary through a CMake script driver
  (`tests/cli/run_case.cmake`) that uses `execute_process` with `WORKING_DIRECTORY` and
  `TIMEOUT 10`, and checks the exit status, a stderr regular expression (empty stderr on
  success), and that stdout is empty. Large and structural cases (nesting, call chains, 2 MiB files, symlinks, FIFOs) are
  generated by the driver at test time into the build directory, never committed.
- Sanitizers: CMake option `PHILIOS_SANITIZE` (default `OFF`) adds
  `-fsanitize=address,undefined -fno-sanitize-recover=all -fno-omit-frame-pointer` to compile and
  link options of every target. Acceptance runs the full suite with it on.
- Static analysis (`clang-tidy`), required by the Verification section of `AGENTS.md`:
  - `.clang-tidy` at the repository root enables `-*,cert-*,bugprone-*`, sets
    `WarningsAsErrors: '*'`, and limits `HeaderFilterRegex` to project headers under `src/`,
    including every nested subdirectory (for example `src/frontend/lexer/`), and under
    `tests/unit/`, including `tests/unit/support/`, so third-party headers are not analyzed.
  - CMake option `PHILIOS_CLANG_TIDY`, default `ON`. When on, CMake locates `clang-tidy` and sets
    `CXX_CLANG_TIDY` on all three project targets, `philios_core`, `philios`, and `philios_tests`,
    so every compiled project file (including every `src/` file compiled into `philios_core`) is
    analyzed during the normal build and any diagnostic fails it. If the option is on and `clang-tidy` is not
    found, configuration fails with a clear message. Developers may turn it off for fast local
    iteration; verification and acceptance always run with it on.
  - Set `CMAKE_EXPORT_COMPILE_COMMANDS ON` so `clang-tidy` and editors can be run against the same
    flags outside the build.
  - Do not disable checks globally to make code pass. Each suppression, whether a `NOLINT(<check>)`
    comment or a check removed in `.clang-tidy`, needs a comment citing the rule and the reason.
  - **Test-only suppression (D36):** doctest's `TEST_CASE` registers tests through dynamically
    initialized static objects, which `cert-err58-cpp` flags and the style guide otherwise forbids.
    `tests/unit/.clang-tidy` sets `InheritParentConfig: true` and disables only `cert-err58-cpp`,
    with a comment citing the rule and this reason, as the AGENTS.md suppression rule requires. It
    is the only file-level suppression in the project, and registration needs no per-test `NOLINT`.
    `src/`, the CLI test scripts, and all other code keep the check. This is a test-only exception
    to the style guide's ban on dynamically initialized static objects; the style guide does not
    change. T-BUILD-5 verifies that the exception does not reach `src/`.
  - The T-BUILD-5 probe (`tests/build/check_tidy_scope.cmake`, registered with `ctest` only when
    `PHILIOS_CLANG_TIDY` is on) uses a committed fixture `tests/build/dynamic_static_init.cpp` that
    defines one dynamically initialized namespace-scope object. The fixture belongs to no build
    target.
  - The T-BUILD-6 probe (`tests/build/check_posix_confinement.cmake`, always registered with
    `ctest`) scans the files under `src/` as text (D32, D45). It matches `#include` lines with any
    whitespace around `#` and `include` and inside the brackets or quotes.
  - **T-CLI-10 registration (D47, D48).** T-CLI-10 is a doctest case in `philios_tests` but is
    registered as its own `ctest` entry. Its exact doctest test-case name is
    `T-CLI-10 terminal device main.phil`. `CMakeLists.txt` holds this name in one variable,
    `PHILIOS_TCLI10_TEST_CASE`, and both entries use it: the dedicated entry runs
    `philios_tests --test-case=${PHILIOS_TCLI10_TEST_CASE}`, and the main `philios_tests` entry
    runs `philios_tests --test-case-exclude=${PHILIOS_TCLI10_TEST_CASE}`. The `TEST_CASE` in the
    test source uses the same string literal. The dedicated entry sets these `ctest` properties:
    - `SKIP_REGULAR_EXPRESSION` matching the line `T-CLI-10 SKIPPED: <reason>`, which the test
      writes to stdout only for a skip outcome (§9 T-CLI-10), so `ctest` reports the test as
      skipped with its reason rather than as passed.
    - `FAIL_REGULAR_EXPRESSION` matching the pinned doctest release's summary line when no test
      case ran (a `test cases:` count of 0, for example the pattern `test cases: *0 *\|`), so a
      filter that matches nothing (a name mismatch between CMake and the source, or a later
      rename) fails instead of passing. The exact pattern is checked against the pinned doctest
      release by T-BUILD-7.
    - `TIMEOUT 10` (seconds, as for the CLI driver), so a hang fails promptly.
    T-BUILD-7 registers a further `ctest` entry, the filter guard: it runs
    `philios_tests --test-case=<a name that matches no test case>` with the same
    `FAIL_REGULAR_EXPRESSION` and `WILL_FAIL TRUE`. It passes only if the pattern really detects a
    zero-test run, so a doctest upgrade that changes the summary format cannot silently disable the
    zero-match check.
  - **Test-only `_exit` exception (T-CLI-10).** The forked child in T-CLI-10 ends every path with
    `_exit`. This is a test-only exception to the style guide's CERT ERR50 rule (no
    `std::abort`, `std::exit`, or `std::terminate`, which skip cleanup), recorded like the D36
    exception: a forked child must not run the parent's `atexit` handlers or LeakSanitizer's
    exit-time check against its copy of the parent's heap, must not flush the parent's duplicated
    stdio buffers, and must not return or unwind into doctest, which would run the rest of the
    suite inside the child's namespaces. `src/` never calls `_exit` (§4). The child closes every
    descriptor it opened before calling `_exit`. The exception covers only the T-CLI-10 test file;
    if a `clang-tidy` check flags the call, it is suppressed with a `NOLINT(<check>)` comment that
    cites this exception, per the AGENTS.md suppression rule.

10. Terminal device (unit, D47, D48, task 4): a `main.phil` that is a terminal device is rejected
    as a non-regular file, and loading it does not give the process a controlling terminal. The
    test is the doctest case named exactly `T-CLI-10 terminal device main.phil` (the value of
    `PHILIOS_TCLI10_TEST_CASE`, §7), is in `tests/unit/cli/` (D44), needs no elevated privileges,
    and uses this mechanism. The test process is single-threaded when it forks (doctest runs tests
    serially and the plan adds no threads), which is what makes the child's non-async-signal-safe
    calls safe; a stray thread makes `unshare` fail, which is a skip, not undefined behavior.
    1. The parent (the test process) creates a fresh temporary directory with `mkdtemp` (so no
       other local user can plant a file in it) and an empty regular file `main.phil` in it, and
       creates a pipe. It opens a pseudo-terminal master with `posix_openpt(O_RDWR | O_NOCTTY)`,
       calls `grantpt` and `unlockpt`, and gets the slave's path with `ptsname`. Cleanup of the
       master, the pipe, and the temporary directory is RAII in the parent, so it also happens when
       a check fails. A failure of `mkdtemp`, of creating `main.phil`, or of `pipe` is a test
       failure.
    2. It forks. Immediately after `fork`, the child closes the pipe's read end, redirects its
       stderr (descriptor 2) to the pipe's write end with `dup2`, and closes the original write
       end. The child calls `setsid()`, so it has no controlling terminal. It then calls
       `unshare(CLONE_NEWUSER | CLONE_NEWNS)`, writes its user and group ID maps (after writing
       `deny` to `/proc/self/setgroups`), makes its mounts private, changes into the temporary
       directory, and bind-mounts the slave onto `main.phil`. A symlink cannot be used, because
       `O_NOFOLLOW` rejects it before `fstat`, and an unprivileged process cannot rename or
       hard-link a devpts node.
    3. Precondition check in the child: `open("main.phil", O_RDONLY | O_NONBLOCK | O_NOCTTY)`
       succeeds, `fstat` reports a character device, and `isatty` is true; the descriptor is then
       closed. If `posix_openpt`, `grantpt`, `unlockpt`, `ptsname`, or `fork` fails (in the
       parent), or `setsid`, `unshare`, the ID maps, the mount calls, or this check fails (in the
       child; for example because unprivileged user namespaces are disabled), the outcome is a skip
       for that named step. Skips happen only in steps 1–3, before any check of `loadMainSource`
       runs. It never asks for or needs root. A failure of `dup2` or of changing into the
       temporary directory is a test failure, not a skip.
    4. The child calls `runTopLevel` with a body that calls `loadMainSource()` and returns 0. The
       result must be 66.
    5. The child then checks that it gained no controlling terminal:
       `open("/dev/tty", O_RDONLY | O_NOCTTY)` must fail with `ENXIO`.
    6. **Child-to-parent protocol.** The child reports its outcome only through its exit status,
       using named constants in the test file's anonymous namespace: a pass code that is neither 0
       nor 1 (for example 10); one distinct skip code per child skip step of step 3 (for example 20
       `setsid`, 21 `unshare`, 22 ID maps, 23 making mounts private, 24 bind mount, 25
       precondition check); and one distinct failure code per failed check (for example 30 `dup2`
       or changing directory, 31 `runTopLevel` did not return 66, 32 `/dev/tty` opened, 33
       `/dev/tty` failed with an error other than `ENXIO`, 34 an exception was caught). The whole
       child body is one `try` block with a final `catch (...)` that maps every exception to its
       failure code. The child uses no doctest macros, never returns into doctest, closes every
       descriptor it opened, and ends every path with `_exit(code)`, the test-only ERR50
       exception recorded in §7. The child writes nothing to stdout.
    7. **The parent's checks.** After `fork` the parent closes its copy of the pipe's write end,
       reads the pipe to end of file, and only then calls `waitpid`, so it cannot hang on a full
       pipe or on its own open write end. It maps the child's status:
       - Exited with the pass code: the parent itself checks that the captured stderr text starts
         with `philios: startup error: main.phil: `; if it does, the test passes, otherwise it
         fails.
       - Exited with a skip code: the parent writes `T-CLI-10 SKIPPED: <reason>` to stdout, where
         the reason names the step the code stands for, and records no failure; `ctest` reports
         the test as skipped (§7). A parent-side skip in step 1 or a failed `fork` writes the same
         line naming that step. The skip line is written only in these two cases, never on any
         path where a check failed.
       - Any other outcome is a doctest failure whose message names the mapped check (for a
         failure code) or the raw status, and includes the captured stderr text: every failure
         code, exit status 0, exit status 1 (for example a sanitizer report), any unknown code,
         and termination by a signal (`WIFSIGNALED`).
       The parent then closes the master and removes the temporary directory. The child's mount
       namespace, and with it the bind mount, ends when the child exits. The dedicated `ctest`
       entry's `TIMEOUT 10` bounds any hang (§7).
    All helpers stay in the test file's anonymous namespace. The test calls POSIX functions from
    test code only; T-BUILD-6 scans only `src/`. On the target environment (Ubuntu 24.04) a skip
    is acceptable; code review then checks `O_NOCTTY` against the §3.2 `open` flags, and the
    acceptance report states per build whether T-CLI-10 passed or skipped, with the reason (D48,

   argument count are checked). In both programs `fail` is an `Integer` function that falls off its
   end, so each exits 70 with class `runtime` at line 1, column 10 (the `fail` name, the
   missing-return error), not at the callee. Over a non-`Function` callee (not the error at `x`,
   line 4, column 12):
   ```
   function fail(): Integer:
       pass
   function call(x: Integer): Integer:
       return x(fail())
   function main():
       return call(1)
   ```
   Over a wrong argument count (not the error at `one`, line 6, column 12):
   ```
   function fail(): Integer:
       pass
   function one(x: Integer): Integer:
       return x
   function main():
       return one(1, fail())
   ```
   A unit test repeats both cases and checks that the raised `RuntimeError` has the
   missing-return kind.

**`null` (T-NULL)**
1. This function, called with `null`, returns `null`; a `null` function using bare `return`,
   `return null`, or falling off the end all return `null` (unit).
   ```
   function n(x: null): null:
       return x
   ```
2. A `null`-returning call used as a statement is accepted; its result passed to a `null` parameter
   works.
3. `null` passed to an `Integer`, `String`, or `Function` parameter, and `return null` from a
   `String` function, exit 70.
4. Unit: (a) (task 3) the execution context's `null` accessor returns the same `NullObject`
   instance every time, and two execution contexts have different instances; (b) (task 8) every
   `null` produced in one execution (the `null` literal, a bare `return`, `return null`, and falling
   off the end of a `null` function) is that context's instance.

**Security and limits (T-SEC)**
1. Call-depth boundaries: generated chains `main → f2 → … → fN` reaching depth 999 and 1,000 exit
   normally; depth 1,001 exits 70 with the call-depth error. These runs must not trip the
   evaluation-depth limit (D24).
2. Direct infinite recursion `f() → f()` and mutual recursion `f → g → f` exit 70 with the
   call-depth error, not a crash.
3. After a call-depth error the depth counter is restored (unit, via the RAII guard).
4. Worst case (D24): a generated program in which `main` returns `f(1)`, `f(x: Integer): Integer`
   returns `g(g(…g(f(x))…))` with calls nested to the parser limit (the innermost argument list at
   nesting level 256), and `g(x: Integer): Integer` returns `x`. It exits 70 with class `runtime`
   and the `evaluation nested too deeply` message, not a native stack overflow, under ASan
   (`build-asan`) and in the release build (`build-release`), each on the default 8 MiB stack. If it
   fails at 10,000, the implementer stops and asks the developer.
5. Evaluation-depth guard (unit, task 3, no AST nodes): the guard is constructed with a
   `SourceLocation`; 10,000 nested entries succeed; the 10,001st raises the evaluation-depth
   runtime error at the `SourceLocation` passed for that entry; the count is restored after the
   exception and after normal exits.
6. Limit precedence (unit, D24): with the call depth at `kMaxCallDepth` and the evaluation depth at
   `kMaxEvalDepth` (both reached through their guards), entering a call expression reports the
   call-depth error at the callee identifier.
7. Diagnostic escaping (unit): a message containing control characters, a CR, and an ESC sequence
   is printed escaped.
8. Top-level handler (unit, D30): with test bodies defined only in `tests/unit/`, `runTopLevel`
   given a body that throws `std::bad_alloc` returns 70 and writes
   `philios: internal error: out of memory`; a body that throws a `std::runtime_error` outside the
   Philios hierarchy, and a body that throws a value not derived from `std::exception`, each return
   70 and write `philios: internal error: unexpected exception`. No exception escapes, and ASan
   reports no leaks.

**Ownership (T-OWN)**
1. Unit: a `std::weak_ptr` observer (test-only) of a `Function` and of the module `Environment`
   expires after `Module` destruction, and `Module::release()` is safe to call twice.
2. Unit: a module that fails validation is not returned.
3. ASan/LSan report no leaks or use-after-free for a normal run and for one run ending in each error
   class (lexical, syntax, declaration, runtime, call depth, evaluation depth).
4. Unit: destroying an AST nested to the parser limit and a long environment chain does not recurse
   per node (verified by destroying a structure far deeper than the limit, built directly in the
   test). The test also builds a structure that makes the destruction worklist long, so a node
   destroyed with its link still set (§3.9 unlink invariant) would recurse through the list and
   overflow the default 8 MiB stack under ASan: a `CallExpr` with at least 200,000
   `IntegerLiteral` arguments (a worklist of at least 200,000 nodes), alongside a chain of at
   least 200,000 nested `CallExpr`s each with one `CallExpr` argument (a deep structure). Each is
   destroyed without a stack overflow or ASan report.
5. Unit (§3.9, CERT DCL57): `static_assert`s confirm that `ASTNode`, every concrete node class,
   `Environment`, and `Module` are nothrow-destructible, and that `ASTNode::detachChildren` and
   `Module::release()` are `noexcept`. A test destroys an AST nested to the parser limit, a
   test-only childless `ASTNode` subclass, and a module environment holding `Function`s, and
   checks with ASan/LSan that no leak or use-after-free occurs. Destruction allocates nothing by
   construction (intrusive AST worklist, loop-unlinked environment chain, table swap), so no
   allocation-failure injection test is built (§3.9 explains why).
