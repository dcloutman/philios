# Plan 0002 — `null`, `Object`, `String`, and `Integer` Types, Negative Integer Literals, and the `echo()` and `typeof()` Pseudo-Functions

- **Target version:** 0.0.1
- **Status:** Ready for review
- **Dependencies:** Plan 0001 (`plans/0001.md`, completed). This plan extends the lexer, parser,
  validator, object model, evaluator, CLI, and test driver built by plan 0001 and replaces the
  plan 0001 rules listed in §3.1. Every plan 0001 rule not listed there still applies.
- **Decision sources:** the developer's draft (traced statement by statement in §3.0) and the grill
  record `plans/0002_grill.md`, session 2026-11-16, decisions D1–D24, confirmed by the developer.
  D13–D24 are developer clarifications quoted verbatim in the grill record. D13, D15, D18, and D22
  carry interpretations marked in the grill record; this plan applies them as recorded and lists
  them for confirmation in §9 (OQ-4, non-blocking). No review round has run yet
  (`plans/0002_review.md` does not exist).
- **Authority:** as plan 0001 did (its D37), this plan is the authoritative source for the language
  rules it introduces. `docs/language_rules.md` is not updated (§9 OQ-3).

## 1. Summary
All types in Philios extend a base `Object` class. Plan 0001 built the object model (`Object`,
`ImmutableObject`, `Integer`, `String`, `NullObject`, `Function`) but gave scripts no output, no way
to inspect a value's type, no general or nullable types, and no negative numbers. This plan adds:

1. **`echo(str)`**, the first output capability: it writes a `String`'s bytes, unchanged, to
   standard output (D13, D14, D24).
2. **`typeof(expr)`**, which returns the script-level name of a value's runtime type as a `String`
   (D3, D12).
3. **Pseudo-functions** as a construct: built-in, callable-only, reserved names that are not
   `Function` values (D8, D20).
4. **`Object` as a declarable type and nullable types `?T`**, with subtype acceptance replacing
   plan 0001's exact typing (D9–D11).
5. **Negative integer literals** `-<digits>`, down to `-9223372036854775808`, without adding any
   operator (D4–D7, D21, D22).

These are needed so a Philios program can produce output (the developer's "Hello World"
acceptance target), so later plans (data structures, arithmetic) have a general `Object` type and
explicit nullability to build on, and so `main` can return negative statuses.

## 2. Scope

### In scope
- The pseudo-functions `echo` and `typeof`: grammar, parse-time checks, evaluation, and errors
  (§3.5).
- Program output on standard output, with every output failure reported (§3.6, D13, D18, D24).
- Declarable types `Integer`, `String`, `Function`, `Object`, `null`, and the nullable forms
  `?Integer`, `?String`, `?Function`, `?Object`; subtype acceptance (§3.4, D9–D11).
- Negative integer literals (§3.2, §3.7, D4–D7, D21, D22).
- Five new reserved words: `not`, `goto`, `isa`, `echo`, `typeof` (§3.2, D2, D20).
- CLI golden-test driver support for checking stdout exactly and for output-failure cases (§7
  task 1).
- Updates to the plan 0001 tests whose expected results these rules change (§8 T-UPD).

### Non-goals
- Unary minus, binary `-`, `+`, `*`, and all other arithmetic (D4). They belong to a future
  arithmetic plan. Nothing here may give `-` an operator meaning.
- The `--` operator, a future C-style decrement operator (D22).
- `not()`, filtering `null` out of data structures, and any meaning for `not`, `goto`, or `isa`
  (D2). They are reserved words only.
- Interfaces, including `ImmutableObjectInterface` (D19).
- Declaring `ImmutableObject`, `NullObject`, `UnsignedInteger`, or `Float` as a type (D11).
- Converting any value to `String`, including a future `Object` method `__toString()` (D16).
  `echo` accepts only `String` values.
- Checking non-literal `echo` arguments before execution, such as a parameter declared `Integer`
  (D17: "Catch typed parameters at runtime for now").
- Any change to `main`: it still takes no parameters and returns `Integer` (D23).
- `Array` and other data structures named in the draft's examples (plan 0010 and later).
- Variables, assignment, classes, instantiation syntax, extension syntax, and function signature
  types (unchanged from plan 0001).
- Signal handling other than the `SIGPIPE` disposition in §3.6. There is still no interrupt flag.
- Output buffering across `echo` calls. Each `echo` flushes (§3.6); performance remains a
  non-goal (plan 0001 D34).
- Updating `docs/language_rules.md` (§9 OQ-3).

### 3.2 Lexical changes

**Reserved words (D2, D11, D20).** The 23 reserved words of plan 0001 §3.3 gain five: `not`,
`goto`, `isa`, `echo`, and `typeof`. Exactly these 28 words are reserved: `function`, `return`,
`null`, `pass`, `Integer`, `String`, `Function`, `Object`, `ImmutableObject`, `NullObject`,
`UnsignedInteger`, `Float`, `if`, `elseif`, `else`, `class`, `extends`, `implements`,
`interface`, `mixin`, `with`, `export`, `import`, `not`, `goto`, `isa`, `echo`, `typeof`. The plan
0001 matching rules are unchanged: case-sensitive, whole-token, emitted as keyword tokens and never
as identifiers. A reserved word where the grammar requires an identifier is a syntax error at the
word (plan 0001 D27). In this plan's grammar, `Object`, `echo`, and `typeof` gain a meaning in
addition to plan 0001's seven words. `not`, `goto`, and `isa` have no meaning (D2).
`ImmutableObject`, `NullObject`, `UnsignedInteger`, and `Float` stay reserved with no meaning
(D11).

**Punctuation.** `(` `)` `:` `,` `-` `?`. Every other character outside strings and comments is
still an unexpected-character lexical error (plan 0001 §3.3).

**`-` and negative integer literals (D4–D7, D21, D22).**
- **Expression-start context (D5, D21).** The lexer is in expression-start context when the
  previous token it emitted is `(`, `,`, or the keyword `return`. These are the only places in this
  plan's grammar where an expression can begin (§3.3). Whitespace, comments, and a `;`
  continuation are not tokens, so `return /*c*/ -1` and a `-1` that begins the continuation line
  after `return;` are in expression-start context. A later plan that adds expression positions
  (for example the right operand of a binary operator, so that `x - -1` subtracts -1, D22)
  extends this list.
- **Negative literal.** In expression-start context, a `-` immediately followed by a digit `1`–`9`
  begins a negative integer literal: the `-` and the longest following run of decimal digits form
  one integer-literal token. Its location is the `-`, and its text includes the `-`. There is no
  whitespace or comment inside the literal.
- **Leading zeros (D7).** In expression-start context, a `-` immediately followed by `0` is a
  lexical error at the `-`. This covers `-0`, `-00`, `-007`, and `-0abc`. Zero is written only as
  `0`.
- **Malformed literal.** A negative literal whose digits are immediately followed by an identifier
  character, for example `-1abc`, is the plan 0001 malformed-number lexical error, at the `-` (the
  literal's first byte). A comment separates tokens (plan 0001 D40): `-1/*c*/abc` is the literal
  `-1` followed by the identifier `abc`, a syntax error at `abc`.
- **Range (D6).** The magnitude must be at most 9,223,372,036,854,775,808.
  `-9223372036854775808` is valid and has the value `INT64_MIN`. A larger magnitude is a lexical
  error at the `-` and is never wrapped. The positive literal `9223372036854775808` remains a
  lexical error (plan 0001 §3.3).
- **Every other `-` is a `Minus` token.** This covers a `-` outside expression-start context (for
  example after an identifier, a literal, `null`, `)`, `pass`, or at the start of a statement), and
  a `-` in expression-start context that is not immediately followed by a digit (followed by a
  space, a tab, a comment, another `-`, a letter, `(`, a line break, or end of file). The grammar
  accepts `Minus` nowhere, so each such `-` is a syntax error at the `-` (D5, D22). Each `-`
  becomes its own token: `--` is two `Minus` tokens and has no meaning. Plan 0002 gives `--` no
  meaning, so a future plan can make it a decrement operator (D22). The future arithmetic plan will
  give `Minus` its subtraction meaning, so `a-1`, `x -1`, and `f(1)-1` stay available (D5, D22).
- **Examples.** Negative literals: `return -1`, `f(-1)`, `f(1, -2)`, `return /*c*/ -1`.
  Lexical errors at the `-`: `return -0`, `return -007`, `return -9223372036854775809`,
  `return -1abc`. Syntax errors at the (first) `-`: `return - 1`, `return --1`, `return -x`,
  `return -/*c*/1`, `return -` at the end of a line, `f(a-1)`, `f(a -1)`, `f(1)-1`, `f(1)-0`,
  `pass -1`, and a statement line `-1`.
- **Conversion.** `[[nodiscard]] std::optional<std::int64_t> parseNegativeDecimalInteger(
  std::string_view digits) noexcept` is added beside `parseDecimalInteger` in
  `src/frontend/lexer/integer_literal.hpp/.cpp`. `digits` excludes the `-`; the lexer has already
  checked that it is non-empty, contains only digits, and does not start with `0`. The function
  parses the magnitude as `std::uint64_t` with `std::from_chars`, requires full consumption,
  returns no value on `std::errc::result_out_of_range` or when the magnitude exceeds 2^63, and
  otherwise computes the result without signed overflow: it negates in `std::uint64_t`
  (`0 - magnitude`, defined unsigned wrapping) and converts the result to `std::int64_t`, a
  conversion C++20 defines (style guide, Integers). No signed expression in it can overflow. The
  lexer raises the located `LexicalError`; the token carries the `std::int64_t` value.
  `parseDecimalInteger` is unchanged.

**`?` (D9, D10).** `?` is a `Question` token. Its only use is the nullable prefix of a type name
(§3.3). Anywhere else it is a syntax error at the `?`.

**Bounds.** Every new lookahead (`-` then a digit, `-` then `0`, a digit then an identifier
character) goes through plan 0001's bounds-checked accessor. A `-` or `?` as the last byte of the
input is read without any over-read (T2-LEX-6).

### 3.3 Grammar
Plan 0001 §3.4 becomes the following. Productions not shown are unchanged. `INTEGER` is a positive
or negative integer-literal token (§3.2).

```
program      := { funcDecl }
funcDecl     := 'function' IDENT '(' [ params ] ')' [ ':' typeName ] ':' NEWLINE block
params       := param { ',' param }
param        := IDENT ':' typeName
typeName     := baseType | '?' nullableBase      ('?' immediately followed by the type word)
baseType     := 'Integer' | 'String' | 'Function' | 'Object' | 'null'
nullableBase := 'Integer' | 'String' | 'Function' | 'Object'
block        := INDENT stmt { stmt } DEDENT
stmt         := returnStmt | passStmt | exprStmt
returnStmt   := 'return' [ expr ] NEWLINE
passStmt     := 'pass' NEWLINE
exprStmt     := ( callExpr | pseudoCall ) NEWLINE   (result discarded)
expr         := INTEGER | STRING | 'null' | IDENT | callExpr | pseudoCall
callExpr     := IDENT '(' [ args ] ')'
pseudoCall   := ( 'echo' | 'typeof' ) '(' [ args ] ')'   (exactly one argument, checked by the parser)
args         := expr { ',' expr }                   (no trailing comma)
```

- **Nullable prefix adjacency (§9 OQ-2).** The `?` must be immediately followed by the type word,
  with no whitespace, comment, or line continuation between them. The parser checks this from the
  token locations: the next token must start on the same line, one column after the `?`.
  Otherwise the error is a syntax error at the `?`. When the adjacent token is `null` (D10), a
  word that cannot be declared (D11), another `?`, or any other token that is not in
  `nullableBase`, the error is a syntax error at that token.
- **Non-declarable type words (D11).** `ImmutableObject`, `NullObject`, `UnsignedInteger`, and
  `Float` in a type position are syntax errors at the word, with or without `?`.
- **Pseudo-call argument count (D17).** A pseudo-call has exactly one argument. `echo()`,
  `echo("a", "b")`, `typeof()`, and `typeof(1, 2)` are syntax errors at the `echo` or `typeof`
  keyword, reported after the argument list has been parsed. A trailing comma is the plan 0001
  syntax error at the `)`.
- **`echo` literal arguments (D16, D17).** If the argument of `echo` is an integer literal
  (positive or negative) or the `null` literal, the parser reports a syntax error at the
  argument's first byte. A string literal is accepted. Every other argument (an identifier, a call,
  or a pseudo-call) is checked when it is evaluated (§3.5).
- **Bare pseudo-function names (D8, D20).** `echo` or `typeof` not followed by `(` is a reserved
  word in an expression or callee position, the plan 0001 D27 syntax error at the word. Examples:
  `return echo`, `apply(typeof, 1)`, `typeof(echo)`, and a statement consisting of `echo`.
- **Nesting (plan 0001 D7).** A pseudo-call's argument list is one nesting level, exactly like a
  call's. Reaching level 257 is the plan 0001 syntax error at the `(` that opens level 257.
- **Other plan 0001 rules carry over.** Calling a call or pseudo-call result (`typeof(1)()`) is a
  syntax error. A pseudo-call may be an expression statement, and its result is discarded, so
  `typeof(1)` alone on a line is valid. Only calls and pseudo-calls may be expression statements.

### 3.4 Types
- **Declarable types (D10, D11).** `Integer`, `String`, `Function`, `Object`, `null`, `?Integer`,
  `?String`, `?Function`, and `?Object`. Types appear only as parameter types and return types.
  `?null` is invalid (§3.3).
- **`main` (D23).** Unchanged from plan 0001: `main`'s return annotation is omitted or exactly
  `Integer`. `?Integer`, `Object`, `?Object`, and every other annotation are the plan 0001
  declaration error at the `main` name.
- **Acceptance (D9).** A declared type accepts values of its subtypes, except `null`, which only a
  nullable type or `null` itself accepts. There is no conversion.

  | Declared type | Accepts runtime values of class |
  |---|---|
  | `Integer` | `Integer` |
  | `String` | `String` |
  | `Function` | `Function` |
  | `Object` | `Integer`, `String`, `Function` (every non-`null` value) |
  | `null` | `NullObject` (`null`) only |
  | `?Integer`, `?String`, `?Function`, `?Object` | what the type without `?` accepts, plus `null` |

  This replaces plan 0001 D14's exact matching. Plan 0001's checks keep their timing, order, and
  locations: the argument type check runs at call time and reports at the argument; the return
  check runs when the function returns and reports at the `return` (plan 0001 §3.7, §4).
- **Return rules with the new types.** Plan 0001's return rules are applied unchanged (§9 OQ-5).
  Only a function declared `null` may use a bare `return` or fall off the end of its body. A
  function declared `Object` or `?T` must execute `return <expr>`; a `?T` function may write
  `return null`. A bare `return` in such a function is the plan 0001 D26 declaration error, and
  falling off its end is the plan 0001 missing-return runtime error.
- **Calls through the new types.** Plan 0001 checks that a callee is a `Function` at call time. A
  parameter declared `Object` or `?Function` can therefore be called; if its value is not a
  `Function` (including `null`), the call is the plan 0001 not-callable runtime error at the
  callee.
- **Script-level type names (D12).** `typeof` maps a value's runtime class to a name: `Integer` →
  `"Integer"`, `String` → `"String"`, `Function` → `"Function"`, `NullObject` → `"null"`. It never
  returns an internal class name such as `NullObject` or `ImmutableObject`. D12 names `"Object"`
  for a value whose most specific declarable type is `Object`; no such value exists in this plan,
  because no plain `Object` can be created.
- **Object model.** No class is added or changed. `Object` stays abstract, so it cannot be
  instantiated (draft). `Integer` and `String` derive from `ImmutableObject`, which derives from
  `Object`; `NullObject` and `Function` derive from `Object` (plan 0001 §3.6). There is no
  `ImmutableObjectInterface` (D19). `null` is the single `NullObject` of the execution context
  (plan 0001 D18).
- **Representation.** `TypeName` in `src/frontend/ast/ast.hpp` gains `Object`. A new plain
  aggregate `struct DeclaredType { TypeName base; bool nullable; }` in the same header represents
  a parsed `typeName`; the parser never produces `nullable` together with `TypeName::Null`.
  `Param::type()` and `FunctionDecl::returnType()` use `DeclaredType`. The single type check of
  plan 0001 §3.6 becomes `[[nodiscard]] bool matchesDeclaredType(const Object& value, DeclaredType
  declared) noexcept` in `src/runtime/evaluator/type_check.hpp/.cpp`, still the only place a value
  is compared with a declared type. The name mapping is one function in the same files,
  `[[nodiscard]] std::string_view scriptTypeName(const Object& value) noexcept`, returning views of
  string literals. Both use `objectType()`; `ObjectType` is unchanged.

### 3.5 Pseudo-functions
- **General (D8, D20).** A pseudo-function is a built-in language construct. It is not a
  `Function` object (the `Function` class exists since plan 0001 D16) and not a value. It can only
  be called: `echo(...)` and `typeof(...)` are the only valid forms. It cannot be referenced,
  passed, returned, typed, or extended, and no function or parameter can share its name, because
  every pseudo-function name is a reserved word.
- **Not a Philios call.** A pseudo-call does not count toward the call depth, creates no
  `Environment`, and runs no call-depth guard. It does count toward parser nesting (§3.3), and its
  `evaluate` starts with the evaluation-depth guard like every node (plan 0001 D24).
- **Argument evaluation.** The single argument is evaluated exactly once and fully, before any
  check, into a named local that holds an owning `std::shared_ptr` for the rest of the
  pseudo-call (style guide, Reentrancy; plan 0001 D6).
- **Validation.** The argument is validated like any expression: undefined identifiers (plan 0001
  D31a) and any use of `main` (plan 0001 D25) are declaration errors, so `typeof(main)` is a
  declaration error at `main`.
- **`echo` (D13–D18, D24).** Signature `echo(String str): null`. Evaluation:
  1. Evaluate the argument.
  2. If the value is not a `String`, raise the runtime argument-type error at the argument's first
     byte (D15, D17). Nothing is written.
  3. Write the string's bytes exactly, through the execution context's output writer (§3.6). If the
     write fails, raise the runtime output-write error at the `echo` keyword (D18).
  4. Return the execution context's `null`.
- **`typeof` (D3, D12).** `typeof` accepts an expression of any type, including `null`, and
  returns a `String`. Evaluate the argument and return a new `String` holding `scriptTypeName` of the value (§3.4). The runtime type
  is reported, not the declared type, so for a parameter `x: Object` holding `1`, `typeof(x)` is
  `"Integer"`. `typeof` has no error of its own beyond those raised while evaluating its argument
  and the evaluation-depth limit.

### 3.6 Program output
- **Destination (D13).** The program's output is standard output. Only `echo` writes to it.
  Diagnostics stay on standard error, in plan 0001's formats.
- **Exact bytes (D24).** `echo` writes the string's bytes exactly as stored: no line break or
  other text before or after, no transcoding, and no escaping. Plan 0001's escaping of control
  characters applies only to diagnostics. An empty string writes no bytes and succeeds.
- **One flush per `echo`.** Each `echo` writes all of its bytes and flushes standard output before
  it returns. A short write or a failed flush is a failure. As a result every output failure is
  detected at the `echo` call that caused it and reported with that call's location (D18), the
  order of output relative to diagnostics on standard error follows program order, and no output
  is pending when the program ends. The interpreter therefore needs no separate end-of-program
  flush step, and the D18 case of a failure found at the final flush cannot arise.
- **Broken pipes (derived from D18; §9 OQ-1).** Before running the program, the interpreter sets
  the disposition of `SIGPIPE` to `SIG_IGN`. Writing to a pipe whose reader has exited then fails
  with `EPIPE` and is reported as the D18 runtime error, instead of the process being killed by
  the signal without a diagnostic. This installs no signal handler and no flag, so the style
  guide's single-interrupt-flag rule is unaffected, and the interpreter starts no child process
  that could inherit the disposition.
- **Output seam.** `src/runtime/evaluator/script_output.hpp` (standard headers only) declares
  `using OutputWriter = std::function<std::error_code(std::string_view bytes)>`. Contract: write
  every byte and flush; return an empty `std::error_code` on success and a non-empty one on any
  failure; never report through `errno`; run no Philios code; throw nothing except
  `std::bad_alloc`. `ExecutionContext` takes the writer in its constructor,
  `explicit ExecutionContext(OutputWriter output)`, stores it by value, and throws `InternalError`
  if it is empty. It exposes `[[nodiscard]] std::error_code writeOutput(std::string_view bytes)`,
  used only by the `echo` evaluation. The context remains non-global and is passed explicitly, so
  this adds no global state (AGENTS.md constraint 1).
- **The shipped writer.** `src/cli/standard_output.hpp/.cpp` declares
  `[[nodiscard]] std::error_code writeStandardOutput(std::string_view bytes) noexcept`, which calls
  `std::fwrite` on `stdout` (skipped for zero bytes) and then `std::fflush(stdout)`. On a short
  write or a failed flush it converts `errno` into a `std::error_code` (`std::generic_category()`)
  immediately, uses `std::errc::io_error` if `errno` is 0, and calls `std::clearerr(stdout)`. The
  same files declare `void ignoreBrokenPipeSignal()`, which calls `std::signal(SIGPIPE, SIG_IGN)`
  and throws `InternalError` if it returns `SIG_ERR`. `runProject` in `src/cli/cli.cpp` calls
  `ignoreBrokenPipeSignal()` and constructs the execution context with `writeStandardOutput`
  before loading `main.phil`. These files use only `<cstdio>`, `<csignal>`, and other standard
  headers, so plan 0001's POSIX confinement (T-BUILD-6) is unchanged.
- **Error message.** The output-write error's message contains the normative phrase
  `standard output`, followed by the reason text of the error code (host text, escaped like any
  diagnostic text).

### 3.7 Negative literals and the exit status
Plan 0001 §3.8 is unchanged: the exit status is `main`'s result modulo 256, computed without
overflow. So `return -1` exits 255 (D1, D21), `return -255` exits 1, `return -256` exits 0, and
`return -9223372036854775808` exits 0.

### 3.8 Runtime architecture changes

## 5. Security and resource limits
- **Malformed input.** The new lexer paths read only through plan 0001's bounds-checked accessor;
  T2-LEX-6 runs each new end-of-input case on exact-size storage under ASan. Negative literal
  conversion uses `std::from_chars` into `std::uint64_t` and unsigned negation, so no input can
  cause signed overflow; out-of-range magnitudes are errors, never wrapped (§3.2). `INT64_MIN`
  reaches the exit-status computation, which plan 0001 already handles (`INT64_MIN` → 0).
- **Nesting and recursion.** No limit changes. Pseudo-call argument lists count toward the parser
  nesting limit of 256, and pseudo-call evaluation counts toward the evaluation-depth limit of
  10,000, so the native stack bound of plan 0001 §5 still holds. Pseudo-calls do not count toward
  call depth, which bounds Philios frames only. T2-TYPEOF-6 tests the nesting boundary and
  T2-ECHO-8 the evaluation-depth guard.
- **Object lifetimes and reentrancy.** `echo` and `typeof` hold an owning reference to their
  argument value for the whole pseudo-call. The output writer runs no Philios code, so `echo`
  starts no reentrant call. `typeof` returns a new `String` object each time. The new AST nodes
  follow plan 0001's iterative, `noexcept`, non-allocating destruction (T2-OWN-2).
- **Output.** Every write failure is reported, never ignored (D18), including `EPIPE` once
  `SIGPIPE` is ignored (§3.6, OQ-1). Script output cannot contain terminal control sequences in
  this plan: string values come only from string literals, which plan 0001 restricts to printable
  UTF-8, tab, and the escapes `\n`, `\t`, `\\`, and `\"` (no control characters other than tab and
  line feed, and no bidirectional formatting characters), and from `typeof` names. Output volume is
  not limited; with recursion a program can write a large amount of output. Like unbounded CPU
  time, this is accepted under the AGENTS.md interim trust model.
- **File handling.** No file is opened besides `main.phil`. If the process starts with descriptor
  1 closed, opening `main.phil` may reuse descriptor 1; plan 0001's loader closes it before
  execution, so `echo` then fails with `EBADF`, which is reported (T2-ECHO-6). There are no
  imports.
- **Numeric edge cases.** No arithmetic is added. The only new numeric operation is the literal
  conversion above.
- **Concurrency.** Single-threaded, unchanged. `SIGPIPE` is ignored process-wide, which is safe
  because the interpreter starts no thread or child process.

blocking; the developer may change any of them before implementation starts.

- **OQ-1: Broken pipes and `SIGPIPE` (derived from D18).** D18 says an output failure is reported
  and returns an error status. With the default `SIGPIPE` action, writing to a closed pipe (for
  example `philios | head -c 1`) kills the process with no diagnostic (shell status 141). Options:
  (A) ignore `SIGPIPE` at startup, so the failure is the D18 runtime error with a diagnostic and
  exit 70, as Python does; (B) keep the default, so the process dies by the signal as many Unix
  filters do, with no diagnostic. **Recommendation: A**, the plan's current rule (§3.6), because it
  is the only option that meets D18's "reports it". Not blocking, because it follows from D18;
  choosing B changes only `ignoreBrokenPipeSignal` and the `broken_pipe` case of T2-ECHO-6.
- **OQ-2: Whitespace after `?`.** May a space or comment separate `?` from the type, as in
  `? Integer`? Options: (A) no, `?` must immediately precede the type word; (B) yes.
  **Recommendation: A**, the plan's current rule (§3.3): it matches the developer's "prefixing"
  wording and D22's treatment of `- 1`, and relaxing it later breaks no program. Not blocking for
  that reason.
- **OQ-3: `docs/language_rules.md`.** Should this plan add the new rules (pseudo-functions, `?`,
  negative literals, stdout) to `docs/language_rules.md`? Options: (A) no, as plan 0001 decided in
  D37; (B) add a documentation task. **Recommendation: A** for consistency with plan 0001. Not
  blocking: it affects documentation only.
- **OQ-4: Confirm the grill record's marked interpretations.** The plan applies them as recorded:
  D13, "the program's output" is standard output; D15, the argument count and literal arguments
  are always checked before execution and everything else at runtime; D18, an output failure is a
  `runtime` error with exit 70 (with one flush per `echo`, every failure has an `echo` location,
  §3.6); D22, "deprecation operator" means a decrement operator, and `- 1` and `--1` are `syntax`
  errors. **Recommendation: confirm as recorded.** Not blocking: each follows the developer's
  quoted words and the error classes D17 defines.
- **OQ-5: Bare `return` and falling off the end in `?T` and `Object` functions.** The plan keeps
  plan 0001's rules (plan 0001 D13 and D26): only a function declared `null` may use a bare `return` or fall off
  its end, so a `?Integer` function must write `return null`. Options: (A) keep that; (B) let a
  `?T` function also use a bare `return` or fall off its end to return `null`. **Recommendation:
  A**, because it changes no existing rule and relaxing it later breaks no program. Not blocking.
- **OQ-6: Plan size.** The plan covers three features: pseudo-functions with output, `Object` and
  nullable types, and negative literals. Options: (A) keep one plan whose tasks are independently
  buildable milestones (§7), as plan 0001 did under its D4; (B) split it into three plans.
  **Recommendation: A** if the developer prefers one review cycle, since tasks 2, 3, and 4–5 are
  already independent; otherwise B. Not blocking.
